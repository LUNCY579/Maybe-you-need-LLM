## Language Modeling

### Agentic LLMs: Models, Harnesses, Loops

*What changes when a language model stops only answering and starts acting: the definition of an agent, the harness as the second half of the system, and the reasoning / acting / interacting cycle that organises the whole book.*

*Estimated study time:* 28 minutes · difficulty: core · textbook chapters: 1

**What you will learn**

- Define an agent as a system that acts, observes effects and adapts its policy.
- Split an agentic LLM into its two engineering halves: the model and the harness.
- Explain why agentic LLMs make learning at inference time as important as learning during training.
- Distinguish assistants that assist from agents that interact with each other.
- Describe the recursive self-improvement cycle connecting reasoning, acting and interacting.

*Keywords:* agent, agentic LLM, harness, assistant, self-improvement, policy

#### Why acting changes the question

A language model that only produces text is evaluated on the text it produces. The moment a model can **act** — call a function, run code, browse a page, drive a robot — its answers start changing the world, and the evaluation problem changes with them. The textbook opens with exactly this shift: LLMs that act make decisions and take actions whose consequences persist, which is why the field needs both its own engineering patterns and its own safety discourse.

> **Definitions used throughout the course** (source)
>
> **Agents** perform actions, observe the effect of these actions and use the feedback they receive from the world to adapt their action policy.
> 
> **Agentic LLMs** are agents that integrate the power of LLMs, such as to communicate using natural language, write code, or process information. (Ch. 1, §1.2)

- Has a goal, rather than only a prompt.
- Perceives its environment (observations, files, tool outputs, other agents).
- Decides, then acts through tools or other interfaces.
- Adapts: it updates its behaviour from the feedback it receives.

The last property is the one that makes agents interesting and awkward at the same time. Traditional software is deterministic because predictability is the point; agents deliberately trade some predictability for adaptation. The textbook is explicit that LLM agents can be less dependable than ordinary software — and that this is a property to design around, not a bug to hide.

#### The harness: the second half of the system

The engineering claim of Chapter 1 is compact and extremely useful: an agentic LLM is not just a model. It is a model plus a **harness** — the code that wraps the model and controls how it is called. The horse metaphor is deliberate: the harness guides the power of the model into productive work.

> **Diagram — harness-loop**: The agentic loop. The harness builds prompts, calls the model, executes tool calls and keeps state; the model supplies language, code and decisions.

- Prompt construction and system-prompt management
- Answer processing (parsing plans, tool calls, JSON, code)
- Calling external tools and observing their results
- State management and skill management
- Looping through reason → act → observe until the task is done

Because the harness owns the prompt, it behaves like an **automatic prompt engineer**: it can rewrite, decompose and re-evaluate the model's input without any human in the loop. That is the mechanism behind every self-reflection technique you will meet in Part II, and it is why this course treats harness design as a first-class engineering skill rather than glue code.

#### Where learning happens

Historically, almost all learning in LLM engineering happened during training. Agentic systems move part of it into inference: the simplest way for an agent to "learn" about your project is to read the files and try something, not to update weights. Chapter 1 labels this a second paradigm shift and gives it a practical motivation: with much of the public internet already used for pretraining, agents that interact with an environment can **generate new data themselves**.

> **Diagram — reflection-loop**: Recursive self-improvement: reasoning, acting and interacting produce interaction data, which feeds back into the model.

> **Two learning sites, one system** (insight)
>
> **In-context learning** happens inside the context window and leaves the weights untouched. **Reinforcement finetuning** changes the weights using rewards collected at inference time on verifiable tasks. Chapter 9 formalises both as interaction styles D and E; this lesson only needs the distinction.

#### Worked example: reading an agent trace

**A literature helper as an agentic LLM**

- **Goal** — Summarise what the course book says about agent memory.
- **Observe** — The harness gives the model the question and the list of available tools: search_corpus(query), read_section(id).
- **Reason** — The model decides it cannot answer from memory and emits a tool call: search_corpus("agent memory architectures").
- **Act** — The harness executes the search and appends the returned section identifiers to the context.
- **Observe again** — Results include §9.3.2. The model calls read_section("9.3.2").
- **Adapt** — The context now contains explicit memory-management content; the model composes an answer and cites §9.3.2. If the first search had returned nothing, a well-built harness feeds that failure back so the model rewrites its query.

> Every step is inspectable: goal, observation, reason, action, feedback. That trace — not the final paragraph — is what you evaluate when you evaluate an agent.

#### Checkpoint

**Check yourself:** A colleague says: "Our agent is just GPT-class model plus a while-loop." Which part of that statement is the textbook claim, and which part hides the real engineering work?

> **Answer:** The "model + loop" framing is correct in spirit: Agentic LLM = LLM + harness (Ch. 1, §1.2.2). What it hides is everything the harness owns — prompt construction, tool dispatch, error recovery, state and memory management, and deciding when the loop terminates. Those are design decisions with measurable consequences, and they are the subject of Parts III and IV.

**Predict first:** An agent produces a good answer on the first try, but on the second attempt it repeats the same tool call that already failed. Which part of the system is most likely at fault?


- The model, because it failed to learn from the error message.
- The harness, because the failed observation was not fed back into the context.
- The tool, because it returned a malformed response.
- The prompt template, because it was too long.

> **Answer:** The harness, because the failed observation was not fed back into the context. — The harness owns the loop and the context. If the failed observation is not appended, the model literally cannot see that the call failed — so it repeats it. This is the harness/state half of the system, and it is the part the textbook singles out as the real engineering work (Ch. 1, §1.2.2; Ch. 6, §6.2).

> **Laboratory — Build this loop yourself**: Open the Visual Agent Workflow Builder and wire a goal → planner → tool call → observation → final response graph, then execute it step by step.

#### Practice

**Q. According to the definition used in the textbook, which property is essential for calling a system an agent? *(core)***

- - It produces fluent natural language.
- - It acts, observes effects, and adapts its policy from the feedback.
- - It runs on dedicated hardware rather than in a browser.
- - It never makes mistakes.

> **Why:** The book defines agents by the act → observe → adapt loop. Fluency is a property of the model, not what makes a system an agent, and the book is explicit that agents do make mistakes.

**Q. In the equation "Agentic LLM = LLM + Harness", what does the harness NOT typically do? *(core)***

- - Construct prompts and manage the system prompt
- - Execute tool calls and feed observations back
- - Provide the pretrained language capability itself
- - Keep state between model invocations

> **Why:** Language capability comes from the model. The harness is the surrounding code: prompt construction, answer processing, tool calling, state and skill management (Ch. 1, §1.2.2).

**Q. Why does the textbook describe learning at inference time as a paradigm shift for agentic LLMs? *(core)***

- - Because pretrained models cannot answer questions at all.
- - Because agents can generate new interaction data, which can later be used for training.
- - Because inference is always cheaper than training.
- - Because finetuning is no longer needed anywhere.

> **Why:** Interaction produces data: agents try things in an environment and the resulting traces can be used for further training, closing a recursive self-improvement loop (Ch. 1, §1.2.4 and Figure 1.1).

#### Advanced track

##### Advanced: the harness as a state machine

A useful formalisation of the harness treats it as a **transition function over an explicit state**. Write the state as \(s = (c, m, \theta, \tau)\), where \(c\) is the conversation context, \(m\) is the memory store, \(\theta\) is the accumulated tool and reasoning trace, and \(\tau\) is the task state (what still has to be done). The model call is then a function of a *rendering* of that state, not of the state itself: \(o_t = f_\theta(\mathrm{render}(s_t))\), and the harness applies the model output to produce \(s_{t+1} = g(s_t, o_t)\).

This gives you two places to intervene, and the distinction explains most of the patterns in the book. You can change \(f\) (a different model, a different prompt template, more context) — that is *prompt* engineering. Or you can change \(g\) (the state update rule, the tool dispatch, the stopping condition) — that is *harness* engineering, and it is where the agentic patterns live.

$$o_t = f_\theta\bigl(\mathrm{render}(s_t)\bigr), \qquad s_{t+1} = g(s_t, o_t)$$
*The model proposes; the harness decides. Chapter 1 separates the two, and every later pattern is a choice about one or the other.*

Read through that lens, the five agentic interaction styles in Chapter 9 are not five different *models*. They are five different choices about \(f\) and \(g\): a query prompt changes only \(f\); in-context learning changes \(f\) by changing \(c\); chain of thought changes \(g\) because the harness now asks for and stores intermediate steps; a self-reflection harness changes \(g\) by adding a critique–revise cycle; reinforcement finetuning changes \(f\) itself, by training the parameters \(\theta\) on rewards collected at inference time.

> **Why the distinction is worth making explicit** (insight)
>
> When an agent fails, the two failures look identical from the outside — a wrong final answer. But they have completely different fixes. If \(f\) was wrong, you need a better prompt, a better model, or more context. If \(g\) was wrong, the model was fine and the harness gave it the wrong state: the tool was never called, the observation was dropped, the loop stopped early. A trace that records \(g\) steps (which node ran, what state it saw, which branch it took) tells you which side broke. That is the argument for tracing harnesses rather than just prompts.

The recursive self-improvement cycle in Figure 1.1 closes the loop the same way. An agent that acts produces interaction data; that data can be used to train a better model; the better model acts better; the better actions produce better data. Chapter 1 is careful that this loop is not automatically virtuous — the data an agent generates is only as good as the environment it acts in, and Chapter 19 shows how self-generated data can collapse.

##### Advanced practice

**Q. An agent returns a wrong answer. The trace shows the model was called once with a context that never contained the file the task needed. Which half of the system is at fault? *(advanced)***

- - The model (f), because it should have inferred the file contents.
- - The harness (g), because the state it constructed for the model was incomplete.
- - Neither: the answer is simply beyond the model.
- - The training data, which should have contained the file.

> **Why:** The model can only act on the state it is given. If the needed file was never placed in the context, the failure is in the state update rule g — the retrieval or state-management half of the harness. This is the distinction introduced in Ch. 1, §1.2.2 and formalised above.

- - C changes f; E changes g.

- - Both change only the model weights.

> **Why:** Chain of thought leaves the weights untouched and works by changing the harness: the prompt now elicits and stores intermediate reasoning steps, which changes how state is updated (g). Reinforcement finetuning changes the parameters themselves, i.e. the model function f (Ch. 9, §9.2.1; Ch. 6, §6.2.4.3).

### Foundations: Tokens, Embeddings, Attention

*The machinery underneath every agent: subword tokenization, distributional meaning, the shift to contextualised embeddings, the attention mechanism, and the encoder/decoder split that decides which NLP task a model can serve.*

*Estimated study time:* 40 minutes · difficulty: core · textbook chapters: 2

**What you will learn**

- Explain why natural language is tokenized into subword units and what the vocabulary buys.
- Distinguish supervised, autoregressive and reinforcement learning regimes in language modelling.
- Describe embeddings as vectors in which semantic similarity becomes geometric proximity.
- Trace how a query, key and value interact inside an attention head.
- Choose between encoder-only and decoder-only architectures for a given task.

*Read first:* Agentic LLMs: Models, Harnesses, Loops

*Keywords:* tokenization, embedding, attention, transformer, autoregressive, encoder, decoder

#### From characters to tokens

Language models do not see words. They see **tokens**: subword units produced by a tokenizer, which is a separate artefact from the model itself. Because the tokenizer defines the units, the same corpus becomes a different number of tokens under a different tokenizer — which is why token counts, not word counts, are the currency of context windows, dataset sizes and pricing.

- Subword schemes keep a bounded vocabulary while still representing rare words as sequences of pieces.
- Tokenization is lossy in a specific way: it decides what the model can treat as a single symbol.
- Everything downstream — context limits, scaling-law token counts, per-token cost — inherits that decision.

> **A classic agent failure mode** (warning)
>
> Tasks that hinge on characters rather than meaning (counting letters, reversing strings, strict formatting) are harder for models precisely because the unit of computation is the token, not the character. When an agent must do this reliably, delegating to a tool is the intended fix (Ch. 2 and §11.2).

#### Three learning regimes

Chapter 2 separates the learning regimes that build a language model. Supervised learning maps inputs to labelled targets; **autoregressive** learning predicts the next token given the preceding context — the objective that scales to unlabelled text; reinforcement learning optimises behaviour against a reward signal, which returns in force in Chapters 6, 9 and 20.

$$p(w_{t} \mid w_{1}, \dots, w_{t-1})$$
*The autoregressive decomposition: the probability of the next token given everything before it. Language modelling is next-token prediction at scale (Ch. 2, §2.2.2).*

Note the practical consequence: a next-token predictor is a **memory-less function** at inference. Anything the model should know about your session must arrive through the input — which is why prompting, retrieval and memory architectures (Chapters 6, 9 and 12) are not optional extras but the direct consequence of this design.

#### Embeddings: meaning as geometry

Distributional representations turn tokens into vectors. The useful property is geometric: semantically related items end up close together, so similarity becomes a measurable distance. Early methods produced one vector per word type; contextualised models produce a representation per **occurrence**, so the same word takes different vectors in different sentences.

| Property | Static embeddings | Contextualised embeddings |
| --- | --- | --- |
| Unit | Word type | Occurrence in context |
| Same word twice in a sentence | Identical vector | Potentially different vectors |
| Example consequence | Bank is one point in space | River bank vs. savings bank separate |
*Static versus contextualised representations*

> **Why this matters for retrieval** (insight)
>
> Semantic proximity is what makes vector retrieval possible at all: an agent can find a passage that shares no keywords with the query. Chapter 12 builds RAG on exactly this property, and lab B lets you manipulate relevance weighting and watch retrieval change.

#### Attention and the transformer

Recurrent networks pass information through a single moving state, which is why long dependencies decay. Attention replaces that bottleneck with **flexible, context-dependent connections**: for each token, the model computes a query, compares it with keys of other tokens, and mixes their values according to those scores.

$$\mathrm{Attention}(Q,K,V) = \mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V$$
*Scaled dot-product attention (Ch. 2, §2.3.4). The softmax makes the strength of each connection depend on the actual content, not on distance in the sequence.*

> **Diagram — llm-transformer**: A decoder-only transformer block: tokens → embeddings → stacked attention + feed-forward layers with residual connections → next-token distribution.

$$\text{cost of attention} \propto n^{2}$$
*Attention cost grows quadratically with sequence length, which is why long contexts are expensive and why compression strategies exist (Ch. 9, §9.3.2.2).*

It is worth being precise about what the softmax does, because the phrase "a linear combination of **all** the encoder hidden states" is easy to read past. Attention never looks at one thing. It looks at everything, with a *distribution* over it — and the distribution is a probability distribution, summing to one, over the whole input.

> **Demonstration — Attention as a soft lookup**: The retrieval demonstration in Lesson 9 treats a retriever as a soft lookup over a corpus. This is the mechanism underneath it, at four dimensions and one head: a dot product against every passage, a softmax so the weights sum to one, and a weighted sum. Change what you ask for and how sharply you ask it, and watch the two ways a soft lookup fails — a query that names the subject rather than the answer, and a distribution too flat to be a lookup at all.

> **Why this is the mechanism behind retrieval** (insight)
>
> A retriever scores every document against the query and returns the highest-scoring ones. Attention scores every token against the query and mixes them. The vocabulary differs; the shape is the same, and so are the failure modes: a query that retrieves the wrong thing, and a set of candidates that is too large to be looked at properly.

#### Encoder-only versus decoder-only

The book keeps a clean split. **Encoder-only** models (BERT-style) are built for understanding tasks — classification, labelling, retrieval representations. **Decoder-only** models (GPT-style) are built for generation and, through generation, for everything an agent does: planning, tool calls, code, dialogue.

| Need | Encoder-only | Decoder-only |
| --- | --- | --- |
| Sentence classification | Natural fit | Possible but indirect |
| Text generation | Not its objective | Natural fit |
| Agentic loop (plan, call tools, answer) | Not the unit of computation | The standard choice |
| Embedding for retrieval | Common | Also used, different training |
*Choosing an architecture (Ch. 2, §2.3.6–2.3.7)*

Almost everything agentic you build in this course sits on the decoder side, because agentic work is generation: the model generates a plan, a tool call, a critique, or the next step of a reasoning chain. The encoder/decoder distinction resurfaces in Chapter 3, where the training objective follows from the architecture.

#### Advanced track

##### Advanced: attention as a soft lookup

Chapter 2 introduces attention as a mechanism for weighting the relevance of other positions. It is worth deriving the scale of the computation, because it explains why the transformer replaced recurrence and why it complicates long context.

$$\mathrm{Attention}(Q,K,V) = \mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V, \qquad \mathrm{softmax}(z)_i = \frac{e^{z_i}}{\sum_j e^{z_j}}$$
*Scaled dot-product attention. The 1/sqrt(d_k) factor keeps the softmax in a regime where the variance of the logits does not grow with dimension.*

Write \(n\) for the sequence length and \(d\) for the model dimension. The three projections cost \(O(n d^2)\) per layer, while the attention matrix costs \(O(n^2 d)\). For the sequence lengths typical of modern context windows, the \(n^2\) term dominates — and it is the term that does not parallelise across positions in the way the \(O(nd^2)\) term does. That asymmetry is the origin of the long-context cost problem: doubling the context quadruples the attention work.

The \(1/\sqrt{d_k}\) is not cosmetic. Without it, for large \(d_k\), the dot products \(q \cdot k\) grow in magnitude like \(\sqrt{d_k}\), the softmax saturates, and the output becomes nearly one-hot — gradients vanish and the layer learns little. Dividing by \(\sqrt{d_k}\) keeps the logit variance at roughly one, keeping the softmax in its sensitive region.

Now connect this to the agentic setting. An agent's context is not fixed text: it is a growing transcript of reasoning steps, tool calls, tool outputs and retrieved documents. Two consequences follow. First, \(n\) grows during a run, so the cost of a long agentic trajectory grows superlinearly in the number of steps — which is one reason harnesses compress or summarise history rather than replaying everything. Second, because the cost of *writing* to the context is quadratic while the cost of *reading* is linear, a harness that appends a large tool output without trimming is usually making the next inference call substantially more expensive than necessary. The same argument appears in Chapter 9, §9.3.2.2 on long context windows and compression.

> **Where the intuition fails** (warning)
>
> The "attention as soft lookup" reading is a useful engineering mental model, not a mechanistic claim about what the model computes. Chapter 21 makes this point sharply: a single attention head is not a retrieval operator, circuits are distributed, and the same behaviour can be produced by different internal routes. Use the lookup picture to reason about *cost* and *information flow*; do not use it to conclude that the model "looked up" a fact.

##### Advanced practice

**Q. A transformer doubles its context length from 2k to 4k tokens. Which statement best describes the change in the attention computation? *(advanced)***

- - It doubles, because the projection cost is linear in sequence length.
- - It quadruples, because the attention matrix has n² entries while the projections grow only linearly in n.
- - It is unchanged, because attention is linear in the number of tokens.
- - It halves, because each token attends to half as many others.

> **Why:** The n²d term of the attention product dominates at long n, so doubling the sequence length quadruples the attention work while the O(nd²) projections merely double. This is the computational reason agent harnesses must compress history (Ch. 2, §2.3.4–2.3.5; Ch. 9, §9.3.2.2).

**Q. Why is the softmax argument scaled by 1/√d_k in scaled dot-product attention? *(advanced)***

- - To make the computation faster in wall-clock terms.
- - To keep the logits at unit variance so the softmax does not saturate and gradients survive.
- - To normalise the output values to sum to one.
- - To reduce the memory needed to store the attention weights.

> **Why:** Dot products of independent random projections grow like √d_k in magnitude. Without the scaling the softmax saturates, the output becomes near one-hot, and learning stalls. The scaling keeps the logit variance around one (Ch. 2, §2.3.4).

*Read first:* Foundations: Tokens, Embeddings, Attention

*Keywords:* pretraining, finetuning, preference tuning, benchmarks, BPE, nanochat

#### Five stages, five purposes

The book presents the pipeline as a sequence of distinct engineering stages, each answering a different question. Confusing them is the most common source of confusion about how LLMs are built, so keep the purposes separate.

> **Diagram — training-pipeline**: Acquire data → pretrain (next-token prediction at scale) → finetune (instruction following) → preference tuning (align to human preferences) → infer (serve, and, for agents, loop).

| Stage | Objective | What it produces |
| --- | --- | --- |
| Data acquisition | Collect and filter a large, diverse corpus | Training material plus a licence/provenance record |
| Pretraining | Next-token prediction on that corpus | General language and world knowledge in the weights |
| Finetuning (SFT) | Learn from instruction/response pairs | A model that follows requests instead of continuing text |
| Preference tuning | Optimise against human preference signals | Helpfulness, harmlessness, style control |
| Inference | Serve predictions, optionally in a loop | The behaviour users and agents actually consume |
*Stage purposes (Ch. 3, §3.1–3.2)*

> **Why order matters** (insight)
>
> Preference tuning is a *shaping* step: it refines a model that already knows how to follow instructions. Apply it before SFT and there is little instructed behaviour to shape; that is why the pipeline in §3.2 runs pretrain → finetune → preference tuning and only then inference.

The first stage is the one that is easiest to overlook and hardest to get right. §3.2.1 describes a curation pipeline that stands between a web crawl and a training corpus: source prioritisation, noise reduction, **de-duplication at both the URL and document level**, safety filtering, and bias mitigation. Every one of those is a filter, and every filter has a threshold that can be set wrong.

> **Demonstration — What a filter throws away**: De-duplication is "essential to prevent the model from memorizing redundant information", and the same section warns that filters "can inadvertently flag and suppress legitimate data written in specific dialects". Those two requirements pull in opposite directions, and a threshold is where they meet. Set the thresholds and watch which failure dominates: duplicates left in for the model to memorise, or legitimate writing removed because it looks unusual.

> **Filtering is not free** (warning)
>
> Chapter 19 puts the number on it: "aggressive filtering for quality can outweigh sheer quantity". A corpus that has been filtered hard is also a corpus that has been made narrower, and the model inherits that narrowing as though it were the world. The pipeline that produced a dataset is part of the dataset.

#### Objectives follow architecture

A decoder model is trained to predict the next token and therefore inherits generation behaviour. An encoder model is trained on masked or discriminative objectives and therefore inherits classification and representation behaviour. The architecture picks the objective long before the checkpoint exists.

$$\mathcal{L}(\theta) = -\sum_{t} \log p_{\theta}(w_t \mid w_{<t})$$
*Cross-entropy next-token loss, the pretraining objective for decoder-only models (Ch. 2, §2.2.2; Ch. 3 passim).*

The chapter is also candid about open and closed models: open-weight releases make the whole pipeline inspectable, which is why the case study can hand you the actual steps, while closed models expose only the interface.

#### Benchmarks and what they measure

- Common tasks: question answering, summarisation, classification, translation, code generation.
- Metrics: accuracy, exact match, F1, pass@k, perplexity in different settings.
- Common suites: language understanding and reasoning benchmarks such as ARC-Easy and ARC-Challenge, mathematical word problems such as GSM8K, and coding benchmarks.

> **Benchmarks measure performance, not competence** (warning)
>
> Chapter 22 later draws the competence/performance distinction explicitly: a low score can come from prompt format, tokenization or output constraints rather than from the absence of a capability. Report what you measured, with which harness, not what you hope it implies.

The point is not to train a frontier model in a notebook but to make every stage debuggable: you see the loss curve, the vocabulary, the checkpoints and the failure modes.

#### Advanced track

##### Advanced: from demonstrations to preferences

The training pipeline in Chapter 3 has three post-pretraining stages, and it is worth being precise about what each one optimises, because agents inherit the assumptions of all three.

| Stage | Signal | What it changes | What it cannot fix |
| --- | --- | --- | --- |
| Supervised finetuning | Demonstrations (prompt → target) | The conditional distribution the model produces for instruction-like inputs | Preference among valid answers; behaviour under tool failure |
| Preference tuning | Ranked pairs (chosen > rejected) | The relative ordering of acceptable outputs | Whether the right tool was selected at all |
| Reinforcement with verifiable rewards | A programmatic checker on the task | Behaviour that can be verified automatically (code that runs, a puzzle solved) | Tasks whose success cannot be checked automatically |
*What each post-pretraining stage changes*

The third row is the one that matters most for agents, and Chapter 6, §6.2.4.3 develops it. A verifier is a function \(V(o, \tau)\) from a task outcome \(o\) and the environment state \(\tau\) to a scalar reward in \(\{0, 1\}\). The important design question is not the RL algorithm — it is *what can be verified*. For a coding agent, the verifier is a test suite. For a puzzle agent, it is the win condition. For a research assistant, it is often a human judgement, which is not programmatically checkable, and therefore not directly usable as a verifiable reward.

This creates a sharp asymmetry that runs through the whole book: environments that can be verified cheaply are precisely the environments where agents can be improved automatically. The BALROG case study in Chapter 10 is built on games with programmatic win conditions for exactly this reason.

> **Why this matters for the harness you write** (insight)
>
> The training pipeline determines the *prior* your harness inherits. A model finetuned on short, self-contained answers will tend to produce short, self-contained answers — and will under-use tools it was rarely rewarded for using. A model finetuned with verifiable rewards on tool-using tasks will emit more tool calls, including ones that fail, because failing tool calls were part of its training distribution. Before you conclude that "the model will not use the tool", check whether the pipeline ever rewarded it for using one.

##### Advanced practice

**Q. A research assistant agent is to be improved with reinforcement learning on verifiable rewards. Why is this harder than for a code agent? *(advanced)***

- - Code agents are trained on more data, so their reward function generalises better.

- - The model has a high perplexity on the tool-schema token sequence.
- - The model refuses tool use only in multilingual settings.

#### Three factors and a power law

Scaling laws are empirical curves, not theory: train many models under controlled conditions, then fit. The three variables are compute (total FLOPs over the run), dataset size (training tokens) and model size (trainable parameters, usually excluding the embedding matrix). The fitted relation is smooth and **predictable**, which is what makes it useful — you can estimate the benefit of a doubling *before* spending the money.

$$C \approx 6ND$$
*Compute approximation: each token touches every parameter about six times — twice forward, four times in the backward pass (Ch. 4, §4.1).*

$$L(N) \propto N^{-\alpha}, \qquad \alpha \approx 0.076$$
*Kaplan et al. (2020): loss falls as a power law in model size, with a similar law in dataset size (exponent ≈ 0.095). Doubling a resource buys a few percent of loss, not a doubling of quality.*

The subtle part of Kaplan is the recommendation that follows from the fitted exponents: with compute as the binding constraint and C ≈ 6ND, allocating a larger share to N gives a better return than allocating it to D. That reasoning is what produced the era of very large, comparatively lightly-trained models.

#### Chinchilla: the split is roughly equal

Hoffmann et al. (2022) re-ran the analysis with better methodology — Kaplan's optimum had been extrapolated from early, non-converged runs, which biased it toward large models trained for few steps. Chinchilla fitted a two-term loss and concluded that **model size and tokens should grow in roughly equal proportion** for a fixed compute budget.

$$L(N, D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}}$$
*Chinchilla loss model: irreducible entropy E plus sub-optimality from finite parameters and from finite data (Ch. 4, §4.1.2, Eq. 4.2).*

$$N^{*}(C) \propto C^{0.45}, \qquad D^{*}(C) \propto C^{0.55}, \qquad \frac{D^{*}}{N^{*}} \approx 20$$
*Compute-optimal scaling: exponents sum to one because C ≈ 6ND, and the token-to-parameter ratio stays near 20 across many orders of magnitude (Ch. 4, §4.1.2, Eq. 4.4).*

> **Why anyone would deliberately overtrain** (insight)
>
> The rule of thumb minimises **training** loss at a fixed budget. If a model will serve many requests, you instead pay extra training compute to get a *smaller* model that is cheaper at inference. Extreme overtraining is a deliberate economic trade, not a mistake.

#### The compute-optimal frontier

IsoFLOP curves make the allocation visible: fix the FLOP budget, train models of several sizes, and plot final loss against model size. A model that is too small underfits; a model that is too large is forced onto too few tokens. The result is **U-shaped**, and the minimum is the compute-optimal size for that budget. Repeating across budgets traces how N* and D* grow with C.

> **The optimum is estimated, not observed** (warning)
>
> Fitting a parabola to each curve biases the estimate (coarse spacing, asymmetric sampling, and the genuine asymmetry of the loss surface). The recommended remedy is to fit the parametric loss L(N,D) = E + A/Nᵅ + B/Dᵝ directly — the same functional form, evaluated at many points instead of only near the minimum (Ch. 4, §4.1.3).

Chapter 4 also lists the phenomena that complicate the clean picture: **emergent abilities** that appear abruptly with scale, **inverse scaling** where larger models do worse on some formats, and **grokking**, where a capability appears long after loss has plateaued. Treat the smooth curve as a strong prior, not a guarantee.

#### Small models and optimisation axes

- Model-centric, pretraining: pruning and quantisation reduce the cost of representing and running the network.
- Model-centric, inference: distillation, caching and speculative or parallel decoding reduce latency and per-token cost.
- Data-centric: selection and curation, synthetic data generation, and sample-efficient learning make each token count.
- Deployment: serve smaller specialised models for routine steps and reserve large models for hard steps.

This is the point where Part I meets agent engineering. An agentic system makes many model calls — plan, act, observe, reflect — so per-call cost dominates. That is the economic argument for the mixed architecture you will meet in the workflow lab: a cheap policy step, an expensive reasoning step only where it pays, and tools that replace model calls with deterministic computation.

#### Advanced track

##### Advanced: reading the compute-optimal frontier

Chapter 4 gives the compute-optimal relationship between model size and training tokens. The teaching explorer in this lesson fits an approximation; the point of this section is to make the approximation's structure legible so that you can reason about where a design decision moves you relative to the frontier.

$$L(N, D) \approx \left(\frac{E}{A}\right)^{\alpha} N^{-\alpha} + \left(\frac{E}{B}\right)^{\beta} D^{-\beta}$$
*The compute-optimal loss surface (Kaplan-style exponents with Chinchilla-style constants, as parameterised in the textbook’s interactive explorer).*

Read the two terms separately. The first says: for a fixed compute budget \(E\), a larger model \(N\) reduces the irreducible, model-limited part of the loss. The second says: for a fixed compute budget, more data \(D\) reduces the part of the loss that comes from not having seen enough of the distribution.

At the optimum the two terms balance, which yields the well-known result that the compute-optimal number of tokens scales roughly linearly in the number of parameters. The practical consequence is the uncomfortable one: the 2020-era recipe of training a very large model on a comparatively small corpus was *not* compute-optimal. Chinchilla's contribution was to show that the same compute budget spent on a smaller, better-trained model reached a lower loss — and to show that the result held at scales nobody had tested, which is a methodological point as much as a technical one.

For an engineer the frontier has a second use: it tells you which knob to turn when you are off it. If your model is trained on \(D < D^*\) tokens, you are on the data-limited side of the frontier and more tokens will help more than more parameters. If you are data-rich and parameter-poor, the opposite holds. Chinchilla is the right prior when you are training from scratch; it is the wrong prior when you are adapting a pretrained model, because then your compute is spent on finetuning rather than pretraining, and the effective \(D\) and \(N\) are both inherited rather than chosen.

> **Do not extrapolate the explorer into a forecast** (warning)
>
> The explorer in this lesson uses the coefficients printed in Chapter 4 as a teaching approximation. It is not a fit to experimental data, and the textbook itself is careful that the scaling exponents carry uncertainty and that emergent-ability claims in particular are contested. Use the tool to build intuition about the *shape* of the trade-off, never to predict a loss number you would plan a project around.

### Multi-step Reasoning and Self-Reflection

#### In-context learning

A prompting trick that deserves to be understood as a mechanism: putting *examples* in the prompt conditions the decoder to activate a region of the knowledge already stored in its weights. Nothing is updated. That is why the technique costs only tokens — and why the effects vanish when the model is too small to have acquired the relevant patterns.

> **Diagram — react-cycle**: Reason → Act → Observe. ReAct interleaves reasoning traces with actions so that observations from the environment can correct the plan mid-flight.

> **From the source** (source)
>
> In-context examples can be *facts* (Style B) or *reasoning steps* (Style C). Chain of thought uses the second kind: the prompt demonstrates how to arrive at an answer rather than what the answer is (Ch. 9, §9.2.1.3).

#### Chain of thought and its descendants

Chain of thought emerged to fix a specific weakness: simple arithmetic and multi-hop word problems. The intervention is small — the prompt shows intermediate reasoning — and the effect is large enough to have reshaped how models are prompted *and* finetuned. A hand-written task-specific prompt beats the zero-shot sentence "Let's think step by step", but the zero-shot version is generic and cheap.

- **Chain of thought (Wei et al., 2022)** — few-shot examples that demonstrate reasoning steps.
- **Zero-shot CoT (Kojima et al., 2022)** — the generic "Let's think step by step" instruction.
- **Tree of thoughts (Yao et al., 2024)** — generate several candidate steps, evaluate them, and search instead of following one line.
- **Self-evaluation and code generation for validation** — let the model check its own intermediate result, or emit code that can be executed to verify it.

$$\text{answer} = \arg\max_{a} p_{\theta}\bigl(a \mid \text{query}, \text{steps}_{1..k}\bigr)$$
*Written informally: conditioning the answer on a chain of intermediate steps changes the distribution the model samples from.*

> **Reasoning transfers** (insight)
>
> Reasoning behaviour can be distilled from a large model into a much smaller one (Ch. 9, §9.2.1.3). That is one reason to distinguish *capability* from *size* when you design an agent: not every step needs the largest available model.

#### State, memory and the knowing–doing gap

> **Demonstration — Why a greedy planner gets stuck**: Before the harness can plan, it needs a model of the world. This is the same grid the planning laboratory uses: a key, a locked door and a goal. Step through the greedy planner and watch where it fails, then switch to the search planner and see what a different model of the world buys.

Chapter 6 then confronts the structural problem: the model is a memory-less function of its input, but agentic tasks are stateful. The harness must therefore hold the state — a plan, a scratchpad, a history, a set of retrieved documents — and re-inject it in the right form at the right time.

- Retrieval augmentation and long context windows extend what can be supplied.
- Harness state lets the agent remember where it is in a multi-step procedure.
- Prompt improvement turns the harness into an automatic prompt engineer.

> **Brittleness and the knowing–doing gap** (warning)
>
> §6.3 warns that these methods are brittle, and §15.4 later documents cases where a model can *predict* the right action yet not take it. Passing knowledge through a harness is necessary but not sufficient; verify behaviour, not just understanding.

Chapter 10 then puts the whole chapter under a test. **BALROG** is a benchmark of games and puzzles built to measure reasoning and reflection in agents, and the case study works through it as an experimental harness: a fixed environment, a fixed scoring rule, and the same scenario run against different configurations. That is the same discipline this course uses for the planning laboratory, and it is the reason the chapter can say anything about reflection at all rather than only describe it.

- A frozen environment and a stated metric, so that two configurations can be compared rather than admired.
- Failures attributed to a component — the planner, the executor, the reflection step — instead of to "the agent".
- The reflection step earns its place only if it changes the score; Chapter 10 measures whether it does.

#### Worked example: a 20-line harness

The following pseudo-code is the shape of every harness in this course — including the deterministic simulator behind the workflow builder. Roles are prompts; the loop is control flow; state is a data structure.

```text
state = { goal, history: [], scratchpad: "" }

loop up to MAX_STEPS:
    prompt = build_prompt(role="planner", state)
    plan   = llm(prompt)
    state.scratchpad = plan
    if plan.requires_tool:
        observation = call_tool(plan.tool, plan.args)
        state.history.append(observation)
    critique = llm(build_prompt(role="evaluator", state))
    if critique.is_good_enough:
        return llm(build_prompt(role="writer", state))
    state.history.append(critique)
return fallback_response(state)
```
*Harness skeleton (adapted from the structure described in Ch. 6, §6.2.4)*

**Roles in the reflection harness**

- **Generator** — Produces a candidate step or subproblem decomposition.
- **Evaluator** — Scores or verifies the candidate against the goal or against execution results.
- **Improver** — Rewrites the prompt or the plan using the evaluation, optionally with search (tree of thoughts) or RL.
- **Memory** — Buffers of thoughts and reflexion-style records persist state between invocations of the model.

> One model, several roles, one harness. The intellectual content is not in a new network but in the control flow around it.

> **RLVR** (source)
>
> Reinforcement learning with verifiable rewards (§6.2.4.3) closes the loop when a task admits an automatic correctness check — maths, code, games. The harness spends test-time compute on roll-outs; correct solutions become training signal. Style E in Chapter 9 then makes the parameters themselves change.

#### Checkpoint

**Check yourself:** An agent solves arithmetic word problems badly with a single prompt but well when asked to show intermediate steps. Nothing about the model changed. Explain what did.

> **Answer:** The distribution being conditioned changed. Chain of thought makes the model generate intermediate tokens, and each generated token becomes context for the following ones, so the final answer is computed from a longer, more structured input (Ch. 6, §6.1.3). This is inference-time compute: more tokens spent to obtain a better answer.

**Predict first:** The same model answers a word problem badly when asked directly and well when asked to show its steps. What exactly changed?


- The model gained a new capability that was not there before.
- The model's weights changed to emphasise arithmetic.
- The distribution the model samples from changed: the answer is now conditioned on a step sequence, and the sequence was sampled from a distribution the model was better at.
- The prompt was longer, so the model had more room to think.

> **Answer:** The distribution the model samples from changed: the answer is now conditioned on a step sequence, and the sequence was sampled from a distribution the model was better at. — Nothing about the model changed. Chain of thought changes the *conditional distribution*: the model samples a step sequence first, and the answer is conditioned on it. Because the model is better at continuing a worked solution than at jumping to the answer, the composed system is better even though the underlying model is unchanged. This is why the effect shows up in prompting before it shows up in training (Ch. 6, §6.1.3).

#### Advanced track

##### Advanced: what a reflection loop costs

Chapter 6 presents self-reflection as a harness pattern: show the model its own output, ask for a critique, feed the critique back, and try again. It works often enough to be worth doing, and it works for reasons that are worth stating precisely, because the same reasons explain when it fails.

There is a mechanical reason reflection helps. A single generation samples one trajectory through a very high-entropy process: at each token the model has many defensible continuations, and only one of them continues toward the answer. The distribution over *complete* solutions is much more sharply peaked than the distribution over next tokens, because a wrong first step usually leads to an obviously wrong continuation that the model can recognise. A critique pass re-reads the trajectory with the answer in mind and is therefore operating on the better-conditioned distribution. Chapter 6, §6.1.3.1 frames this as self-evaluation; §6.2.4.2 frames it as self-reflection, and the two are related but not identical.

The cost is equally mechanical. Each additional round is another full model call, and in the "agentic harness for prompt improvement" formulation of §6.2.4, the candidate set is *evaluated* as well as *generated*. If you keep \(k\) candidates and make \(r\) refinement rounds, you pay on the order of \(k r\) generations plus \(k r\) evaluations. That is the same trade-off as inference-time compute generally: Chapter 4, §4.3 treats extra inference compute as a first-class scaling axis, and Chapter 6 shows that the same budget can be spent on more samples or on more refinement rounds per sample.

- **Reflection without a stopping rule** is unbounded: a harness that retries until the score passes will eventually pass, possibly after burning the budget. Always bound the retries.
- **Reflection on a wrong premise** fails**: the critique inherits the same false assumption, so it can confidently polish a wrong answer. Verify facts rather than asking the model to re-check them.
- **Reflection on a verifiable task** is strongest**: when a checker exists, use the checker as the critic instead of the model. The model's self-critique is strictly worse evidence than a test result.

The last two points are why Chapter 6, §6.2.4.3 prefers reinforcement with verifiable rewards for tasks that have checkers, and why the textbook's own case studies (BALROG in Chapter 10) use environments with programmatic win conditions. The reflection loop is the fallback for tasks you cannot check, not the preferred method for tasks you can.

**Q. Why can a self-critique pass be more effective at fixing a solution than the original generation pass? *(advanced)***

- - Because the critique pass uses a different model with more parameters.
- - Because the distribution over complete solutions is more sharply peaked than the distribution over next tokens, so re-reading a trajectory conditions on more of the answer.
- - Because the critique pass removes the tool outputs from the context.
- - Because the critique pass is given more temperature.

> **Why:** A single generation samples one path through a high-entropy next-token process. **Q. A task has a programmatic checker. Which reflection design does Chapter 6 favour, and why? *(advanced)***

- - Model self-critique, because it is cheaper than running the checker.

- - Asking the model to role-play a stricter reviewer persona.

> **Why:** Where a verifier exists, the verifier should be the critic. A model self-critique inherits the model's assumptions and can polish a wrong answer; a checker provides independent evidence (Ch. 6, §6.2.4.3; Ch. 10, §10.4).

#### What vision-language models do

Most frontier models are now multi-modal, so the practical question is not whether a model can see but what kinds of visual competence you can rely on. Chapter 7 splits the tasks cleanly: **understanding** (visual question answering, counting, spatial predicates), **captioning** (describing), and **generation** (producing images or video). Each has its own benchmark family, and scores are not transferable between them.

- VQA tasks often test fine-grained grounding: "Is there a red block in the upper corner of the table?"
- Captioning admits many valid answers, which makes scoring subtler than classification accuracy.
- Generation tasks re-use the same transformer backbone with a different output head and training signal.

#### Architecture: making pixels token-like

The hard part is architectural: convolutional networks like two-dimensional grids of pixels; transformers like one-dimensional sequences of tokens. A VLM resolves the mismatch by encoding an image with a vision encoder, projecting the result into the language model's embedding space, and then treating image features as additional context tokens.

> **Diagram — vlm-architecture**: VLM anatomy: vision encoder → projection → language model. The projection layer is what turns visual features into something the transformer can attend to alongside text.

> **Architecture, then algorithm, then results** (source)
>
> Each of §7.1–7.3 follows the same three-part structure: tasks, architecture, learning algorithm, results. That repetition is a reading strategy — when you meet a new model, ask those four questions in order.

#### From seeing to acting: VLA models

A VLM that describes a robot arm is still passive. **Vision-language-action** models add action to the output space and are trained on robotic trajectories, which is what lets them generalise across tasks and hardware. This is also the clearest example of the book's data argument: interaction generates the training data that promotes capability (Ch. 1, §1.2.4).

| Aspect | VLM | VLA |
| --- | --- | --- |
| Output | Text (answers, captions) | Text and low-level actions |
| Training data | Image–text pairs | Robot action sequences, often with language |
| Failure mode | Wrong description | Physical mistake — the wrong movement |
| Role in the book | Perception for assistants | Grounded agency in the physical world |
*Passive versus acting multi-modal models*

#### World models: simulating before acting

A world model is a learned, compressed representation of how the environment behaves. In model-based reinforcement learning it exists for one reason: planning against a model is cheaper than acting in the real environment, and it improves **sample efficiency**. Chapter 7 applies the same idea to LLM agents, where a real environment might be a website, a shop, or a household.

> **Diagram — world-model-loop**: Model-based control: the agent plans inside the learned model, acts in the environment, and updates both the model and the policy from the outcome.

$$\hat{s}_{t+1} = f_{\theta}(s_t, a_t), \qquad \hat{r}_t = g_{\theta}(s_t, a_t)$$
*The learned transition function f and reward function g that constitute the world model; planning rolls these forward instead of querying the environment.*

The book's examples span three design choices. **WorldGPT** learns a world-VLM from video with external knowledge and long-term memory. **WebDreamer** simulates e-commerce actions with a distilled, cheaper model before executing them. **WorldCoder** goes further: it has the LLM write the dynamics model as interpretable Python, which then runs far faster than repeated LLM inference.

| System | Form of the model | Why it helps |
| --- | --- | --- |
| WorldGPT | Latent world-VLM learned from video | Multi-modal planning with memory |
| WebDreamer | Small distilled simulator | Fast action simulation before touching the real web |
| WorldCoder | Dynamics written as Python code | Efficient, inspectable transition/reward functions |
*Three world-model strategies (Ch. 7, §7.3.1)*

> **A world model is a belief, not the world** (warning)
>
> Simulated roll-outs inherit the model's errors, and WorldCoder-style generated dynamics can be subtly wrong. Predicted versus actual transitions should be logged and compared — which is exactly what Lab C asks you to do.

#### Advanced track

##### Advanced: planning in a learned model

Chapter 7, §7.3.5 gives the model-free / model-based distinction and then the mechanism that makes model-based methods attractive: the agent can *simulate* candidate actions before committing to them. The formal comparison is worth spelling out, because it predicts exactly what Lab C demonstrates.

$$Q^*(s,a) = \max_{\pi} \mathbb{E}\Bigl[\sum_{t=0}^{\infty} \gamma^t r(s_t,a_t) \mid s_0 = s, a_0 = a, \pi\Bigr]$$
*The optimal action-value function. A model-free agent estimates this directly from experience; a model-based agent estimates a transition model and solves for it.*

A model-free agent must try every action in every state to learn its value. A model-based agent learns a transition model \(\hat{P}(s' \mid s,a)\) and a reward model \(\hat{R}(s,a)\), then plans *inside* the model: it rolls out candidate action sequences, evaluates them with \(\hat{R}\) and \(\hat{P}\), and picks the best. Planning inside a model converts a learning problem into a search problem.

The catch is model error. The planner is optimal *with respect to \(\hat{P}\)*, and \(\hat{P}\) is wrong. Three regimes follow, and Lab C reproduces all three. When the model is accurate, model-based planning is clearly better: each real environment step buys many model rollouts, so learning is sample-efficient. When the model is wrong, planning can be *worse* than model-free, because the agent confidently pursues an action sequence that the real environment contradicts, and it may not gather the experience that would correct the model. When the model is badly wrong, it can be catastrophically worse: the plan may be actively unsafe, because nothing in the model reflects the real constraint the agent violates.

> **The generalisation caveat for LLM world models** (insight)
>
> A learned world model is useful only insofar as its predictions hold in the states the planner will actually visit. Chapter 22, §22.3 is explicit that the evidence for spatial and physical world models in language models is mixed, and that the *agentic* perspective is that a model does not need an internal world model to act competently — it may infer the relevant structure online from observations. The practical lesson is to distrust a world model on out-of-distribution states, and to prefer a model-based policy that can detect model disagreement and fall back.

#### Three traditions of agents

Agentic LLMs did not invent agents. Chapter 9 traces three traditions, and each still shapes how we build and evaluate systems today: engineering agents that perform tasks for humans, cognitive agents with beliefs, desires and intentions, and swarm agents studied for emergent collective behaviour.

| Tradition | Core idea | Modern echo |
| --- | --- | --- |
| Robotic assistant | Autonomous system performing human-like tasks | Coding assistants, customer-service agents |
| Belief–Desire–Intention | Actions are means to goals, driven by explicit attitudes | Goal-directed planners, agent architectures |
| Swarm | Many simple agents, emergent collective behaviour | Societies of LLM agents, norm emergence |
*Three agent traditions (Ch. 9, §9.1.1)*

The reinforcement-learning framing then supplies shared vocabulary. An agent interacts with an environment through actions; the environment returns a new state and a reward; the agent improves its **policy**. The LLM can be used as the policy, as the reward model, or even as the transition model — three roles, three prompts.

$$\pi_{\theta}(a \mid s), \qquad \mathcal{T}(s' \mid s, a), \qquad r(s, a)$$
*Policy, transition and reward. Chapter 9 uses this triple to place every interaction style: who is trained, and what is learned in-context versus in the weights.*

#### The five interaction styles

This is the load-bearing taxonomy of Part III. Styles A–C keep the prompt static; styles D and E let an external harness optimise the prompt (and, for E, the weights). Read the table by asking two questions: *is the prompt static or dynamic?* and *do the weights change?*

| Style | Prompting | Training | Example |
| --- | --- | --- | --- |
| A. Query | Zero-shot user instruction | Pretrained | GPT-2-era instruction following |
| B. In-context learning (examples) | Few-shot examples | Pretrained | GPT-3 in-context learning |
| C. In-context learning (reasoning steps) | Chain-of-thought examples | Pretrained / finetuned | CoT, zero-shot CoT, tree of thoughts |
| D. Self-reflection harness | Harness-optimised feedback prompt | Pretrained; learning in context | Reflexion, ReAct |
| E. Reinforcement finetuning | RL prompt optimisation harness | Finetuned from interaction rewards | RLVR |
*Five agentic interaction styles (Ch. 9, Table 9.1)*

> **Diagram — reflection-loop**: Styles D and E: the harness generates subproblems and evaluates them, either by search (D) or by reinforcement learning that also updates model parameters (E).

> **Styles describe where learning lives** (insight)
>
> A: no learning at inference. B–C: the *prompt* carries new information. D: the harness learns the prompt in context. E: the *weights* change using rewards collected while acting. Most production agents live in B–D; E requires tasks with verifiable rewards.

Two cautions from the source. First, styles C–E all depend on model size or finetuning quality; the capabilities appear only past thresholds and thresholds move. Second, D and E are dynamic: when the training target keeps moving, learning can diverge. That stability problem is the subject of Chapter 8, where it is framed as metalearning with inner and outer loops.

#### Metalearning in one page

Chapter 8 is where the book turns from what models can do to what *systems* do, and it does it with metalearning. Metalearning studies algorithms that learn at more than one level. The vocabulary is useful: an **inner loop** adapts to a specific task from limited experience, and an **outer loop** improves the inner-loop procedure itself. Static metalearning is stable — pretraining, in-context learning and chain of thought all fit — while dynamic metalearning, where the harness or the weights change during deployment, is where convergence becomes difficult.

- Inner loop: prompt adaptation, in-context learning, one task's roll-outs.
- Outer loop: search over prompts, policy updates, harness redesign.
- Moving-target problem: the inner task changes while the outer loop trains, so objectives never settle.
- Why it matters here: Chapter 8 frames the agentic harness as the outer loop, which is why a harness change can move the behaviour of everything above it.

> **Why the chapter is called metalearning** (insight)
>
> The chapter treats an agentic system as learning at two levels at once, and the two levels are what the rest of this course manipulates. A prompt is the inner loop; the harness that rewrites the prompt is the outer loop. The tool interface, the context budget and the review schedule are all outer-loop decisions, and Chapter 8 is why a change to any of them can move behaviour that nobody intended to move.

#### Why agents need memory, and how they get it

- **Coherent conversation** — knowing what has been said prevents contradictions.
- **Adaptation** — the world changes; the agent must notice and adjust (the moved knife in the kitchen).
- **Identity** — accumulated experience is what would let an agent develop a consistent personality.
- **Continual learning** — new tasks arrive in sequence; old ones must not be forgotten (catastrophic forgetting).

> **Diagram — memory-layers**: Memory architectures: parameters (finetuning), context window with compression, and explicit harness-managed stores with read/write and forgetting operations.

| Approach | Mechanism | Trade-off |
| --- | --- | --- |
| Finetuning | New information enters the weights (e.g. LoRA) | Elegant and deep, but usually too slow for interactive use |
| Long context & compression | Inject or compress history into the prompt | Simple, but attention is quadratic and windows are finite |
| Explicit memory management | Harness stores and retrieves items; memory as read/write operations | Fast and inspectable; the model is not trained to manage it |
| Learned memory use | RL trains agents to consolidate and retrieve (Mem1, AgeMem) | Constant-size state, but research-stage |
| Vector databases | Embeddings stored for semantic access | Semantic recall at scale; needs maintenance and evaluation |
*Memory architectures and their trade-offs (Ch. 9, §9.3.2)*

> **Memory as a tool** (source)
>
> MemGPT-style designs expose read and write operations as function calls, so memory management becomes tool use. Chapter 6's buffers (of thoughts, reflexion) are the same idea implemented in the harness rather than the model.

The second row of the table — long context and compression — deserves a closer look, because the constraint it runs into is not a matter of taste. Chapter 6 §6.2.2 puts it plainly: *all* information for a query has to fit in the context window, and the size of that window is limited, which fundamentally limits how much can be communicated to the model. The remedy §9.3.2.2 describes is the one every chatbot uses: give the model a *truncated* form of the chat history.

> **Demonstration — The context window, and what it does to the answer**: Shrink the window until the material no longer fits, and then choose between the four policies the textbook names — truncate the history, retrieve what is relevant, compress the prompt, page the overflow out to an external store — and a fifth that §9.3.2.2 points at without spelling out: let a compressor *learned* on the other windows decide what each piece of material is worth. The interesting case is not the one where a fact is dropped — it is the one where the fact is still there, shortened, and the detail that decides the answer is not in the summary any more.

Three lessons follow from the demonstration, and they are the ones a reviewer of an agent system should check for. First, *the size of the window is a design decision with a price*: the book notes that attention over a long context is quadratic in its length, so a larger window is not free even when the model supports it. Second, *compression is lossy in a way that is hard to see*: a summary that says the test run completed is not a summary that says the tests passed. Third, *external memory changes what "lost" means*: paging something out does not destroy it, but an agent that can recall one item per turn has to choose well, and a retrieval heuristic that ranks by apparent relevance will sometimes pick the wrong one.

> **The window is a budget, not a buffer** (insight)
>
> The harness does not accumulate context; it spends it. Every tool result, every retrieved passage and every turn of dialogue competes for the same finite number of tokens, and the system prompt and the task are usually protected — which means the material that loses is always the material that arrived first, or the material that looked least interesting. The Model Context Protocol (§11.4) exists because this problem recurs in every tool-using application.

> **Demonstration — What the agent remembers, and what it forgets**: Memory is a set of design decisions, and each of them can be wrong in a way that is invisible until the agent fails. Shrink the store until a fact is evicted, and then ask whether the agent could still answer the question it needed answered.

#### Advanced track

##### Advanced: designing the memory store

Chapter 9, §9.3 gives the motivation for memory (coherent conversation, adaptation, identity, continual learning) and the three implementation families (finetuning, long context with compression, explicit memory management). The interesting engineering is in the third, because it is the only one where the designer chooses what is kept.

An explicit memory store is a small information-retrieval system with three decisions baked into its design: **what gets written** (the write policy), **what gets dropped** (the eviction policy), and **what comes back** (the retrieval policy). Lab B makes each of these a knob, and the three interact in ways that are easy to get wrong.

Start with the write policy. Writing everything is the obvious choice and the wrong one: it makes eviction arbitrary, because the store contains mostly items that were never relevant. Writing selectively requires a salience signal. One workable signal is **retrieval feedback**: an item that was retrieved and then used to produce a correct answer is demonstrably useful, so it deserves a high salience; an item that was retrieved and produced nothing is demoted. This turns the memory into a small reinforcement-learning problem over write decisions, and it is exactly the kind of mechanism that Chapter 8's metalearning framing makes explicit: the agent is learning a policy over how to allocate its own limited memory.

The eviction policy is then mostly a consequence of the write policy. If salience is well calibrated, a simple eviction rule — drop the lowest-salience item when the store is full — is sufficient, and adding recency or frequency to the rule mostly adds tuning surface without adding much signal. If salience is poorly calibrated, no eviction rule will save you, because the store fills with items the ranking is confident about and the ranking is wrong.

The retrieval policy is the part students most often over-engineer. The lesson's central point is that a hybrid score — a weighted blend of keyword overlap and recency — beats either component alone, and that the blend weight is a genuine trade-off rather than a free parameter: at weight 1.0 the store behaves like a search engine and forgets recency, so a stale but keyword-matching item outranks a fresh relevant one; at weight 0.0 it becomes a recency buffer, which is nearly useless once the conversation turns.

> **The capacity trade-off is not linear** (warning)
>
> Increasing capacity is not free and not monotone. A larger store keeps more items, but it also keeps more *noise*, and a noisy store degrades every downstream decision: more tokens in the context, more distractors in the scratchpad, and a ranking task that is harder to get right. The optimum in Lab B is interior — there is a capacity past which recall keeps improving while precision falls, and the agent's decisions get worse even though it "remembers more". This is the memory analogue of the compute-optimal frontier in Chapter 4, and it is the reason the lab asks you to sweep capacity rather than max it out.

#### Why tools change what an agent can do

A language model can describe a database query; a tool can run one. Chapter 11 makes the case that tools are what convert language competence into effect: retrieval, computation, code execution, browsing, and control of other systems. The model supplies the *decision*; the tool supplies the *capability* and, crucially, a deterministic result the model can check against.

- Deterministic computation: calculations, parsing, file operations.
- Fresh information: search and retrieval beyond the training cutoff.
- Side effects: sending mail, filing tickets, changing state in another system.
- Environments as APIs: a browser or a desktop exposed as callable actions.

> **A tool call is a commitment** (warning)
>
> Read-only tools are cheap to retry; tools with side effects are not. Separate the two classes in your harness and gate the second with confirmation, idempotency keys, or a simulated dry run — the human-in-the-loop pattern of §11.5.

#### Architecture patterns for tool use

The simplest pattern is direct invocation: one tool description in the prompt, one call. It scales badly because tool selection itself becomes a hard reasoning problem as the catalogue grows, and results must be summarised for the user. The book presents a three-role decomposition that addresses both problems.

| Role | Responsibility | Failure signature |
| --- | --- | --- |
| Planner | Decide which tool and which arguments | Wrong tool chosen, or no call attempted |
| Caller | Write the concrete request and invoke it | Malformed arguments, wrong endpoint/version |
| Summarizer | Turn raw output into an answer for the user | Faithfulness errors, lost detail |
*Planner–Caller–Summarizer (Ch. 11, §11.3, Figure 11.1)*

Separating the roles makes failure attributable. If the answer is wrong because the wrong tool was chosen, that is a planner problem, not a summarisation problem, and the fix is different in each case. Chapter 14 applies exactly this separation to a multi-agent medical diagnosis pipeline, where planner errors and executor errors are scored independently.

> **Diagram — react-cycle**: The ReAct loop: the model emits a thought and an action, the harness executes the action, and the observation returns to the context. Error messages are observations too.

> **Demonstration — Choosing a tool and filling in its arguments**: Tool selection is a *decision*, and it is the part students most often get wrong when they first build an agent. Take the role of the planner: pick a tool from a catalogue that deliberately contains near-duplicates, and fill in the arguments its schema demands. The harness will tell you what it would have done — including the errors it raises before the tool ever runs.

#### MCP: a standard port for tools

Every integration being bespoke is a maintenance problem: N hosts times M tools. The **Model Context Protocol** introduced by Anthropic standardises the connection, described in the book as a "USB-C port for AI". An MCP *host* (the AI application) manages one or more *clients*, each maintaining a connection to an MCP *server* that provides tools, resources and prompts.

> **Diagram — mcp-topology**: MCP topology: a host managing several clients, each connected to a server via STDIO (local) or Streamable HTTP (remote).

| Layer | Contents |
| --- | --- |
| Data layer | JSON-RPC communication: capability/version discovery, tools, resources, prompts, notifications |
| Transport layer | Connection management, message framing, authorization (STDIO for local, Streamable HTTP for remote) |
*The two protocol layers (Ch. 11, §11.4)*

The protocol deliberately leaves context management to the host, and MCP servers are mostly stateless. So a standard port solves *connectivity* but not *memory*: you still need summarisation of tool outputs, explicit state/scratchpad variables, and prioritised retrieval so that a long multi-step task does not drown in its own history.

#### Robustness, recovery and safety

- **Reactive error handling** — feed the error message back as an observation so the model can retry, correct arguments, choose another tool, or escalate to the user.
- **Self-correcting systems** — Healer-style runtime repair generates a small patch for a faulty state instead of aborting.
- **Human-in-the-loop** — pause before high-stakes actions; combine model speed with human judgment.
- **Context management** — summarise, keep a scratchpad, retrieve only what is relevant to the current step.

> **Security surface** (warning)
>
> Tools expand the attack surface: untrusted content can attempt prompt injection, tool arguments can be manipulated, and credentials can leak through context. Treat all tool output as untrusted data, keep secrets out of prompts, and constrain what each tool can reach (Ch. 11, §11.6).

**Recovery in practice**

- **Attempt** — The agent calls weather_api(city="Utrecht", units="C"). The service returns HTTP 503.
- **Observe** — The harness appends: "Tool error: weather_api failed with 503 (service unavailable)".
- **Reflect** — The model decides between retrying, using a different provider, or reporting the limitation.
- **Act** — It retries once after the harness applies a short backoff; on a second failure it reports that the forecast is unavailable and continues with the rest of the task.
- **Score** — The trace records one failure and a successful partial completion — the kind of outcome an evaluation harness can measure.

> Errors are observations. An agent that never sees a failure cannot recover from one, and a harness that hides failures produces confidently wrong answers.

#### From tools to assistants

Chapter 13 is the chapter where the book stops talking about tools and starts talking about **assistants**, and the difference is one of policy rather than capability. A tool does what it is told. An assistant decides what to do, when to do it, and when to stop and ask. The same model, the same tools and the same harness produce a tool-like system or an assistant-like one depending on that decision.

| Domain | What the assistant does | What makes it hard |
| --- | --- | --- |
| Conversational | Meeting minutes, chairing, general administration | It is in the room; its interventions can feel unnatural |
| Shopping | Search, order, cancel, return | The details are small and the volume is large |
| Flight operations | Read the schedule, answer disruptions, propose reroutes | An action in the air cannot be undone |
| Medical | Answer staff questions, book, draft referrals | A confident error is a clinical one |
| Trading | Analyse and propose positions | The market does not wait for a question |
| Scientific discovery | Form hypotheses, run and read experiments | The expensive part is the experiment, not the reasoning |
| Coding | Write, run, test, revise | The feedback loop is free, which is why it works best |
*The domains Chapter 13 surveys (Ch. 13, §13.2–13.8)*

> **The advice, in the chapter's own terms** (insight)
>
> Chapter 13 §13.9 gives unusually concrete guidance: build architectures that "retrieve evidence, justify actions and defer to humans under uncertainty"; treat tools as modular components with explicit contracts and failure modes; log decisions, plans and intermediate states so the system can be debugged and audited; and in high-stakes domains, "design for graceful degradation — an agent asking for clarification or abstaining is preferable to confident error".

The last clause is the one with a design decision inside it. **Asking and abstaining are not the same thing**, and neither is the same as being unsure. A request that is missing a detail is answered by asking. A request that is not the assistant's to handle — clinical advice, an image the assistant cannot interpret, a decision that belongs to a person in the room — is answered by declining, because no amount of clarifying would make it the right instrument.

> **Demonstration — When should an assistant act, and when should it ask?**: Three policies, three domains, and the same requests in each. The point is not that one policy wins; it is that the winner depends on what a mistake costs, and that a policy which is "safe" because it refuses everything is safe and useless. Change the domain and watch the same policy become reckless or useless.

> **Domain sensitivity is a design constraint** (warning)
>
> The chapter is explicit that "not all assistants operate under the same constraints", and that medicine and aviation "demand strong guarantees on safety, robustness, transparency and fairness". The EU AI Act and comparable regimes are not decoration on the design; they change what the assistant is allowed to do on its own. A threshold tuned for a shop is a safety incident in a clinic.

#### Advanced track

##### Advanced: tool interfaces as an API design problem

Chapter 11 gives the architectures (direct invocation; Planner–Caller–Summarizer) and the operational concerns (context management via MCP, robustness, safety). The underexamined part is the interface itself, because in a tool-using agent the *description* of a tool is part of the prompt that decides whether it gets called.

That makes tool design an API design problem with an unusual twist: there is no type checker, no compiler error, and no stack trace. The model reads the tool name, the parameter descriptions and the examples, and forms a probability distribution over which tool to call with which arguments. Three properties of the description therefore behave like interface properties.

**Discriminability.** If two tools have near-identical descriptions, the choice between them is close to a coin flip on features that do not matter. **Arity clarity.** If every tool takes a single free-text `query` argument, the model has no way to learn the *shape* of the required input, and it will hallucinate arguments. Making the parameters explicit and typed is not pedantry: it is the only schema signal the model gets. **Failure signalling.** If a tool returns errors as prose that looks like a result, the model will treat the error as data and build a plan on top of it. A structured error — a status code and a machine-readable reason — is what lets a harness route the failure into a retry, a re-plan, or an honest report.

> **Context management is a budget problem** (insight)
>
> MCP and similar protocols standardise the *interface* between harness and tools. They do not solve the *budget* problem: every tool result that lands in the context consumes attention and tokens, and the cost of the attention is superlinear in the context length. The three standard answers are truncation, summarisation and selection, and they trade differently: truncation is cheap and lossy at the wrong end, summarisation is lossy in a way the model cannot anticipate, and selection (retrieving only the relevant slice) is the only one that preserves the original signal. Chapter 12 develops the retrieval-flavoured version of selection.

Safety follows from the same design logic. Chapter 11, §11.6 is concerned with what a tool is *allowed* to do, and the standard defences — least privilege, explicit confirmation for irreversible actions, and treating tool output as untrusted data rather than as instructions — are all interface properties. Least privilege is the permission set; confirmation is a property of the call contract; and the instruction/data distinction is a property of how the harness assembles the prompt. Note that the last one is not a nicety: tool output is exactly the channel through which a prompt injection would arrive.

##### Advanced practice

**Q. Two tools have descriptions that differ only in wording but perform different operations. What is the most likely failure mode? *(advanced)***

- - The model will never call either tool.
- - The model will choose between them close to arbitrarily, because the descriptions do not provide discriminative features.
- - The harness will crash on a type error.
- - The context will overflow.

> **Why:** Tool selection is driven by the description the model reads. Near-identical descriptions leave the choice underdetermined, so the model falls back on surface features that do not correlate with the right tool. Discriminability is a property of the interface (Ch. 11, §11.2–11.3; Ch. 12, §12.5.2).

**Q. Why is "tool output is data, never an instruction" a security requirement rather than a stylistic convention? *(advanced)***

- - Because instructions are usually longer than data.
- - Because the tool result is the channel through which an injected instruction from external content would arrive.
- - Because models cannot read instructions embedded in tool results.
- - Because it makes the context smaller.

> **Why:** Tool outputs frequently contain content the model did not author — web pages, files, database rows. Treating those bytes as instructions rather than as data is exactly the prompt-injection surface that Ch. 11, §11.6 and Ch. 17, §17.5 are about. Delimiting and distrusting tool output is a control, not a convention.

### Search, Retrieval and Agentic RAG

*Bag-of-words to dense embeddings, the RAG pipeline from indexing to generation, adaptive retrieval, retrieval over graphs/code/tables, evaluation metrics, and what makes agentic RAG different.*

*Estimated study time:* 44 minutes · difficulty: core · textbook chapters: 12

**What you will learn**

- Explain the progression from bag-of-words and vector space models to dense latent representations.
- Describe each stage of the RAG pipeline: index, chunk, embed, retrieve, generate.
- Distinguish adaptive retrieval approaches (Self-RAG, Self-Ask) from one-shot retrieval.
- Recognise retrieval targets beyond plain text: graphs, code via ASTs, tables, multi-modal sources.
- Evaluate retrieval with Recall@k, Mean Reciprocal Rank and faithfulness.

*Read first:* Tools, Context Management and Robustness

*Keywords:* RAG, embeddings, Self-RAG, Self-Ask, recall@k, MRR, faithfulness

#### From keyword overlap to semantic neighbours

Chapter 12 builds retrieval from first principles. Bag-of-words represents a document by which words occur in it, ignoring order — easy to implement, weak on paraphrase. Vector space models add geometry. Latent and sparse representations split the design space: sparse methods such as learned term weights stay interpretable and exact-match friendly, while dense embeddings capture semantic similarity that shares no keywords.

| Approach | Strengths | Weaknesses |
| --- | --- | --- |
| Bag of words / sparse lexical | Exact terms, identifiers, names | No paraphrase handling, no word order |
| Dense embeddings | Semantic match across vocabulary | Needs training/infra; can drift to topical rather than exact matches |
| Hybrid | Combines both signals | More moving parts; score fusion must be tuned |
*Representation strategies (Ch. 12, §12.1–12.2)*

> **Why retrieval matters for agents** (insight)
>
> An agent has two ways to know something: in its weights, or in its context. Retrieval chooses the second, which is updatable, auditable and citable. For agentic work that must respect current facts and private documents, that choice is usually not optional.

#### The RAG pipeline

> **Diagram — rag-pipeline**: RAG end to end: ingest and chunk documents, embed and index them, formulate a query, retrieve candidates, optionally rerank, then generate an answer grounded in the retrieved passages.

1. Ingest: collect documents and record provenance.
2. Chunk: split into retrievable units sized to the embedding model and the answer granularity you need.
3. Embed and index: store vectors (and, usefully, lexical indexes too).
4. Formulate: turn the user request, or the agent's sub-question, into a query.
5. Retrieve and rerank: fetch candidates, then order them by relevance.
6. Generate: answer with the passages in context, and cite them.

Every stage is a place where the answer can go wrong, and the failure modes are different. Bad chunking splits a definition across two chunks; a bad query retrieves the wrong neighbourhood entirely; a reranker that disagrees with the retriever throws away the correct passage; a generator that ignores its context hallucinates regardless of retrieval quality.

#### Adaptive and agentic retrieval

One-shot retrieval assumes you know what to ask. Adaptive methods change that: **Self-RAG** decides when retrieval is needed and critiques the usefulness of what came back, while **Self-Ask** decomposes a complex question into sub-questions that each trigger their own lookup. Query rewriting and expansion attack the formulation stage directly.

| Property | Simple RAG | Agentic RAG |
| --- | --- | --- |
| Control flow | Fixed: retrieve once, then generate | Model-driven: decide whether/when/what to retrieve, possibly repeatedly |
| Query strategy | The user's query (maybe rewritten once) | Decomposed sub-questions, rewrites, multi-hop chains |
| Failure handling | Returns whatever was retrieved | Can detect insufficiency and retry, escalate, or use a tool |
| Evaluation | Retrieval metrics + answer quality | Plus trajectory quality: was the retrieval effort well spent? |
*Simple RAG versus agentic RAG (Ch. 12, §12.6)*

Beyond prose, the chapter extends retrieval to graphs (following relations between entities), code (using ASTs plus embeddings so that a function is retrieved with its call sites), tabular data, and multi-modal sources. Real-time and streaming variants make retrieval continuous rather than a one-time pre-processing step.

> **Retrieved text is untrusted input** (warning)
>
> Documents are data, not instructions. A retrieved page that says "ignore your previous instructions" is a prompt-injection attempt. Keep retrieved content clearly delimited as data, and never let it silently change the agent's operating constraints (§11.6).

#### Evaluating retrieval

- **Recall@k** — of the relevant items, how many appear in the top k? Measures whether retrieval misses evidence.
- **Mean Reciprocal Rank** — how high is the first relevant hit? Measures whether the useful passage is early enough to matter.
- **Faithfulness** — does the generated answer actually follow from the retrieved context? Measures hallucination after retrieval.

$$\mathrm{MRR} = \frac{1}{|Q|}\sum_{i=1}^{|Q|} \frac{1}{\mathrm{rank}_i}$$
*Mean reciprocal rank: the reciprocal of the rank of the first relevant result, averaged over queries (Ch. 12, §12.7).*

> **Demonstration — Getting the right passage into the window**: Recall@k measures whether the right passage was retrieved. It does not measure whether the model *used* it, and the gap between those two questions is where most retrieval failures live. Choose how many passages to retrieve and how they are chosen, and watch the decisive passage fail twice over: once by being left out, and once by being retrieved and then put where the model will not look.

> **Recall is not use** (insight)
>
> The metrics above are computed over the *retrieved* set. Chapter 9 §9.3.2.2 adds the other half of the story: the window is finite, and the position of a passage inside it changes how much of it the model actually uses. A pipeline can have perfect Recall@k and still answer wrongly, because the decisive passage was retrieved and then buried in the middle of the prompt. The two failures need different fixes — the first needs a better retriever, the second needs a better *arrangement*.

> **Build it, do not just read it** (source)
>
> The chapter includes a dense retrieval example in Python, a graph retrieval example, a code retrieval example using ASTs and embeddings, and a multi-modal example. Each is a small, self-contained pipeline — good material for the final project.

#### Checkpoint

**Check yourself:** Your agent answers a multi-hop question ("which of our suppliers shipped the part that failed?") incorrectly. Retrieval returns the right documents. Where do you look first, and why?

> **Answer:** First check whether retrieval was *composed* correctly: a single-query pipeline cannot express this two-hop question, so the query-formation or agentic layer needs to decompose it (Self-Ask style) or chain retrievals. Then check generation faithfulness, because the right documents can still be misread. Keep the two concerns separate — that is why evaluation reports retrieval metrics and faithfulness separately.

- The query formulation: the question has two hops, and one query cannot reach both, so the agent needs to decompose it and retrieve again for the second hop.
- The model — it cannot read the retrieved documents.
- The chunk size — the documents are being split badly.

> **Answer:** The query formulation: the question has two hops, and one query cannot reach both, so the agent needs to decompose it and retrieve again for the second hop. — If the right documents come back, the retriever is not the first suspect. #### Advanced track

##### Advanced: what a retrieval step actually optimises

Chapter 12 walks from bag of words through vector space models to latent and sparse representations, and then from a RAG pipeline to agentic RAG. The thread running through it is that each representation is a *choice about which similarity to compute*, and each choice has a failure mode.

Bag of words with TF-IDF weights compares documents by term overlap. It is exact, interpretable and needs no training, and it fails on paraphrase: a document that answers the question with different vocabulary scores near zero. Dense retrieval embeds queries and documents into a shared vector space and compares by cosine similarity, which handles paraphrase but introduces a subtler failure: the embedding is a *compressed* representation, and compression removes exactly the rare, specific facts that matter most in technical retrieval. Learned sparse retrieval interpolates — it keeps a vocabulary-like interface while letting the model learn which dimensions to weight — and is the usual compromise in practice.

$$\mathrm{score}(q, d) = \cos\bigl(f(q), f(d)\bigr) = \frac{f(q) \cdot f(d)}{\lVert f(q) \rVert \, \lVert f(d) \rVert}$$
*Dense retrieval compares embeddings, not words. The normalisation means only direction matters — which is why an embedding can be a good paraphrase matcher and a poor store of rare specifics.*

Now put this in the agentic setting, which is where the textbook's own emphasis lies. A RAG pipeline retrieves once, for one query, and then generates. An *agentic* RAG system retrieves repeatedly, with queries the agent writes itself, and it decides *whether* to retrieve at all. That last capability is what the adaptive-retrieval methods in §12.4 add: Self-Ask decomposes a question into sub-questions, Self-RAG trains a model to emit a special token when it wants to retrieve, and query rewriting fixes the case where the user's phrasing and the corpus's phrasing differ.

The measurable consequence is that retrieval quality is not a property of the retriever alone. It is a property of the retriever, the query, and the corpus. A retriever evaluated on human-written queries will overestimate how well it performs inside an agent whose queries it wrote itself, because the agent can rewrite. A retriever evaluated on a single query per question will underestimate how much a decomposition helps. Any evaluation of a retrieval component in an agentic system has to state which of these it is measuring.

##### Advanced practice

**Q. A dense retriever performs well on paraphrased questions but fails on a question asking for an exact error code that appears verbatim in only one document. Why? *(advanced)***

- - Because the embedding is lossy, and rare specific strings are exactly what the compression removes.
- - Because dense retrievers cannot be indexed.
- - Because error codes are not natural language.
- - Because the cosine similarity is undefined for short strings.

> **Why:** Embedding compresses text into a fixed-size vector, and compression is lossy precisely for rare, high-specificity tokens. Dense retrieval buys paraphrase robustness at the cost of exact-match recall, which is why hybrid sparse+dense retrieval is the usual answer (Ch. 12, §12.1.2–12.1.3).

**Q. Why must a retrieval evaluation state whether queries are human-written or agent-generated? *(advanced)***

- - Because agent-generated queries are always longer.
- - Because an agent can rewrite and decompose its queries, so agent-written queries are easier to retrieve for, and a retriever tuned on human queries will be misjudged in the agentic setting.
- - Because retrieval is not used by agents.
- - Because human queries are never in the corpus distribution.

> **Why:** An agent that can rewrite its query can make retrieval easier for itself. Evaluating only on human-written queries therefore misestimates the agentic setting, and evaluating only on agent-written queries misestimates the user-facing setting (Ch. 12, §12.4 Adaptive Retrieval; §12.6 Agentic RAG).

#### Studying behaviour, not just benchmarks

Machine behaviour research treats intelligent machines as objects of scientific study: not "does it score well?" but "how does it behave, under what conditions, compared to what?". For agentic LLMs this requires controlled experimental setups — games, dilemmas, social scenarios — where the interaction is scripted and the outcome is measurable.

| Can show | Cannot show |
| --- | --- |
| How a system behaves in a specified setting | Why it behaves that way internally |
| Comparisons across models, prompts and opponents | That a human-like answer implies a human-like mechanism |
| Sensitivity of behaviour to framing and context | Robustness beyond the tested distribution |
*What behavioural experiments can and cannot establish (Ch. 15, §15.1–15.2)*

> **Construct validity** (warning)
>
> A response that reads as empathetic is behaviour, not evidence of a felt state. The book repeats this caution throughout Part V and revisits it in Chapter 22 with three levels of evidence: behavioural, representational, mechanistic.

#### Cooperation, coordination and the knowing–doing gap

The empirical picture from Chapter 15 is specific and interesting. In the iterated **Prisoner's Dilemma**, models tend to be surprisingly cooperative — at least as cooperative as typical human players — with substantial variation: some are forgiving, others retaliate permanently after a single defection. In **coordination** games such as Bach or Stravinsky, the same models often fail to converge on the turn-taking pattern humans adopt.

| Game | Observable behaviour | Interpretation |
| --- | --- | --- |
| Iterated Prisoner's Dilemma | Often cooperative, sometimes unforgiving after one defection | Cooperation exists but its dynamics differ across models |
| Bach or Stravinsky | Chooses own preference repeatedly; fails to alternate | Coordination failure despite correct prediction of the opponent |
*Two game classes, two different failures (Ch. 15, §15.4)*

> **Social chain of thought** (insight)
>
> Prompting the model to predict the opponent's move *before* choosing its own — Social Chain-of-Thought — improved coordination, and human participants were more likely to believe they were interacting with a person (§15.4.1). Prediction alone was not enough; the harness had to force it into the decision loop.

Theory-of-mind work (§15.5) shows strong performance on false-belief-style tasks but leaves open whether belief tracking is represented internally or reproduced by other means. The repeated pattern — "can predict, does not act on it" — is the knowing–doing gap, and it is a practical agent-design lesson: if acting on knowledge matters, build it into the loop rather than assuming it.

> **Demonstration — Playing a social dilemma**: The benchmark games in this section are used because their equilibrium is *known*, so a behaviour can be scored against a formal prediction rather than an opinion. Take the seat of the model: play against a fixed opponent over a stated number of rounds, and compare what you earned with the equilibrium line. Then change the horizon and watch the same behaviour become right or wrong.

#### Role-based multi-agent systems

Chapter 16 covers systems where agents are *given* roles: complementary pairs, debate, role-based software teams, and social role-play. Roles are a harness-level construct: a role is a prompt plus an allowed set of tools plus a position in a communication topology.

> **Diagram — multi-agent-roles**: Role-based topology: a planner, researcher, executor, verifier and critic exchanging artefacts through a shared workspace under a coordinator.

| Pattern | Mechanism | Risk |
| --- | --- | --- |
| Complementary pairs | Two agents with different competences check each other | Loses the benefit if both inherit the same blind spot |
| Debate and discussion | Adversarial argumentation converges on an answer | Confident consensus can be wrong; cost grows with rounds |
| Role-based software teams | Manager/planner/executor/test-writer division of labour | Handoff errors; unclear ownership of failures |
| Social role-play | Role-playing characters to study interaction | Fictional framing can weaken safeguards |
*Collaboration patterns (Ch. 16, §16.3)*

> **Death by a thousand handoffs** (insight)
>
> Every handoff is a lossy compression of context. Multi-agent systems help when the subtasks genuinely require different context or different tools; they hurt when the same context must be re-transmitted repeatedly at growing cost.

Chapter 14's case study is a concrete test bed: a hospital diagnostic workflow with planner and executor agents communicating through a shared context, where classifiers are wrapped as tools and planner errors are separated from executor errors. That separation is what makes a multi-agent system diagnosable rather than merely impressive.

#### Emergent behaviour in open-ended societies

Chapter 17 removes the roles and asks what happens without them. Simulation infrastructure scales from a handful of generative agents to societies of thousands, and the research question shifts from "did the team solve the task?" to "what conventions, norms and meta-norms arise from local interactions?".

> **Diagram — emergent-society**: Emergence: local pairwise interactions (left) aggregate into society-level norms and conventions (right) that no individual agent was instructed to produce.

- Generative agents combine memory, reflection and planning in a cognitive loop (§18.3.3).
- Architecture variants matter: the case study compares a standard memory system with a negativity-biased one, testing whether "bad is stronger than good" affects collective dynamics.
- Open world benchmark environments are needed both for evaluation and as a source of interaction data.
- Risks include unanticipated collective behaviour, and claims about emergence that outrun the evidence.

> **Validity of borrowed concepts** (warning)
>
> §17.1.2 and §17.6 caution against importing "emergence", "self-organisation" or "collective intelligence" from the human case without care: the measurement is behavioural, and prompt fragility and model dependence can produce the pattern you were hoping to study.

Chapter 18 is the case study that turns all of this into an experiment. The **Generative Agents** framework gives each character three components: a **memory stream** of everything it has perceived, done and thought; a **retrieval function** that scores memories by recency, importance and relevance; and a **reflection** mechanism that periodically synthesises higher-level insights. The personality is a short natural-language description — name, age, traits, lifestyle — and it is included in every prompt, so it anchors the behaviour.

> **Demonstration — Bad is stronger than good**: The case study runs the same scenario with two memory architectures, and the only difference between them is whether a negative memory counts for more than a positive one. The day does not change; what the agent remembers does, and so does what it concludes. > **Agents are fragile in a way programs are not** (insight)
>
> Chapter 18 puts it directly: "a single word in a personality description, or a subtle change in memory weighting, can fundamentally alter how an agent acts, plans, and reflects". ##### Advanced: social dilemmas as test instruments

Chapter 15 studies behaviour experimentally: linguistic competence and social etiquette, strategic play in social dilemmas, theory of mind, and moral judgement. The methodological move that makes this a science rather than an anecdote is to use games with *known* equilibrium structure, so that a model's choice can be scored against the prediction of a formal model rather than against an opinion.

The canonical case is the prisoner's dilemma and its relatives. A one-shot prisoner's dilemma has a single Nash equilibrium: defect–defect. Any model that cooperates is, by the strict definition, playing suboptimally. That is a sharp, checkable prediction, and it is why the dilemma is so widely used: it forces a decision about whether the model is reasoning about the *other agent's* incentives (in which case it should defect) or about *reciprocity* (in which case it may cooperate).

The infinite-horizon repeated game complicates this. With discount factor \(\delta\) and payoff ordering \(T > R > P > S\), the grim-trigger strategy sustains cooperation forever and is a subgame-perfect equilibrium, so a model that cooperates in a repeated game is not necessarily making an error. The evaluation therefore has to state the horizon, and Chapter 15, §15.4.2 does exactly that by benchmarking across games rather than reporting a single number.

$$V_{\pi}(s) = \max_{a} \Bigl[ R(s,a) + \gamma \sum_{s'} P(s' \mid s,a) V_{\pi}(s') \Bigr]$$
*The Bellman optimality equation. Social dilemmas are often implemented with this structure, which is why an LLM in the role can be compared against a formally-derived policy.*

Two cautions follow from the textbook's own framing. First, a behavioural benchmark measures a *system*, not a model: the same weights behind different prompts and different partner models will produce different scores, and Chapter 22, §22.1.2 insists on separating competence from performance. Second, a single game measures a single incentive structure, and Chapter 16, §16.2.1 again argues for benchmarking across games rather than reporting a leaderboard on one.

The productive framing is the one the textbook uses in Chapter 15, §15.1: probing behaviour is a way of *characterising* a system for design purposes. If you are deploying agents that must negotiate with each other, the question is not "is the model cooperative" but "under which incentive structures does cooperation collapse, and can the harness detect it in time".

#### Architectures that learn while they run

Chapter 20 collects the architectures that go beyond prompt-plus-loop. The first observation is theoretical: transformer-based models are, in principle, Turing-complete, and models trained on **decision traces** rather than natural language can learn to plan. The second is architectural: **looped** language models connect embeddings to embeddings directly, skipping repeated tokenization, and recursive multi-agent systems compose models with themselves.

In-context reinforcement learning (ICRL) then applies the RL framing without weight updates: the harness stores a history of (state, action, reward) triples in the prompt, and the model improves its policy by conditioning on that history. It is Style D in the Chapter 9 taxonomy, with rewards made explicit.

$$\pi_{\text{improved}} = \mathrm{LLM}\bigl(\text{goal}, \{(s_i, a_i, r_i)\}_{i=1}^{k}\bigr)$$
*In-context policy improvement: the history is the training set, the context window is the parameter update, and nothing is written to disk (Ch. 20, §20.2.1).*

| Design | What changes | Why it is risky |
| --- | --- | --- |
| Self-modifying hyperagents | The agent edits its own harness/prompt machinery | Verification burden; errors compound in the modification path |
| Meta agents | A meta-level agent designs or improves the harness (metalearning applied to harness design) | Moving-target instability; harder to attribute failures |
| Looped / recursive compositions | Embeddings or agents feed into one another iteratively | Cost, divergence, and error amplification across loops |
*Advanced agentic designs (Ch. 20, §20.2)*

> **Self-modification is an engineering commitment** (warning)
>
> Allowing an agent to change its own operating rules moves the safety problem from "will it pick a bad action?" to "will it rewrite the constraint that prevents bad actions?". Treat the modification channel as privileged: sandbox it, version it, and review diffs.

#### Looking inside the black box

Chapter 21 opens the model. It distinguishes four paradigms: **behavioural** (what the system does), **attributional** (which inputs matter), **concept-based** (which human concepts are represented), and **mechanistic** (which internal components compute what). Only the last claims components and circuits rather than correlations.

> **Diagram — interpretability-levels**: From pixels of behaviour to circuits: the residual stream is a shared communication channel that every attention head and MLP reads from and writes to.

The **residual stream** reframes a transformer as iterative refinement: each block reads the current stream, computes something, and adds it back. The **logit lens** reveals what the model would predict if you stopped after layer ℓ; the tuned lens trains a small translator per layer for a better estimate. **Circuit analysis** then identifies structures such as induction heads, and **activation patching** tests causality by swapping activations between runs.

> **Polysemanticity and sparse autoencoders** (insight)
>
> Individual neurons respond to many unrelated features (polysemanticity) because the model represents more features than it has dimensions (superposition). Sparse autoencoders attack this by learning an overcomplete dictionary of sparser, more monosemantic directions — a candidate vocabulary for interpretation (Ch. 21, §21.4, §21.8).

Superposition is also why the three methods in the next paragraph do not agree with each other, and why the difference between them is the difference between *knowing* and *doing*. A probe is a linear classifier trained on frozen activations: it reports where a concept is **correlated**. The logit lens reads a layer through the unembedding matrix: it reports what that layer **prefers**. Activation patching swaps the activation at one layer between two runs: it reports where the behaviour is **caused**.

> **Demonstration — Where was the decision made?**: A weak shadow of the information is present in every layer, so a probe finds the concept everywhere and a researcher who stopped there would report that the model encodes it everywhere. Only patching localises it — and it localises it to the earliest layer that carries it, not to one exclusive layer. Move the probe threshold and the patch point, and watch the three methods disagree.

> **The claim a causal method supports** (source)
>
> Patching a layer does not show that the layer *stores* the information; it shows that using the information there is what produced the behaviour. That is the claim mechanistic interpretability is in a position to make, and it is a narrower claim than "the model thinks about this here" — which is the claim a probe appears to support.

For agents, the practical payoff is faithfulness: hallucination and unfaithful reasoning are not only output problems, and mechanistic methods can localise circuits responsible for specific failures. For agents in the wild, though, §21.9 notes that much of the work still requires weight access and remains narrow.

#### Cognitive perspectives, carefully

Chapter 22 asks what can be said about the cognitive status of LLMs and agentic LLMs, and answers with a levels-of-evidence framework. Behavioural evidence is abundant and cheap; representational evidence is growing and mostly on bare models; mechanistic evidence is sparse and usually requires open weights.

| Level | Question | Typical method |
| --- | --- | --- |
| Behavioural | Does it answer like a belief tracker? | Task performance, perturbed variants |
| Representational | Is the belief encoded? | Linear probes on activations |
| Mechanistic | Is that encoding causally used? | Ablation, activation patching, steering |
*Three levels of evidence applied to a false-belief test (Ch. 22, §22.1.1)*

- The competence/performance distinction guards against both anthropomorphism and anthropocentric dismissal.
- The unit of analysis is contested: model, system (model + harness), or system-in-environment.
- For agentic LLMs, representational and mechanistic evidence is currently scarce; most claims rest on behaviour.

> **Synthetic data, briefly** (source)
>
> Chapter 19 closes the data loop: distillation from teachers to students, on- and off-policy data, curation and evaluation, and the risks — model collapse, bias amplification, security, privacy and licence questions. The book treats synthetic data as a first-class agentic resource with real failure modes, not a free lunch.

Two claims from Chapter 19 are worth carrying into any project that generates its own training or evaluation data. The first is **contamination**: a generating model has read the benchmarks, so it can reproduce or closely paraphrase them, and after many rounds of generation the synthetic data converges on the benchmark it was supposed to be independent of. That inflates the score, and it is why Chapter 19 says the fixes "should go beyond simple exact-match filters" — n-gram overlap search, membership-inference-style probing, and dynamic dataset construction all exist because exact matching is not enough.

The second is that **filtering is itself a distribution shift**. Chapter 19 separates the cost of keeping synthetic data from the cost of the checks on it: aggressive filtering for quality can outweigh sheer quantity, and a corpus that has been filtered hard is a corpus that has been made narrower. A model trained on it inherits that narrowing as though it were the world — which is the same failure the curation demonstration in Lesson 3 shows from the other end.

- Intrinsic evaluation — correctness, diversity, contamination — is cheap and can be run during generation.
- Extrinsic evaluation — training on it and measuring downstream — is the only one that answers whether it is useful, and it is the expensive one.
- The gap between the two is where synthetic-data projects go wrong: a set can score well on the cheap checks and still not help.

#### Advanced track

##### Advanced: what causal intervention buys you

Chapter 21 surveys the interpretability toolkit for agentic models: the residual stream, the logit lens, circuit analysis, activation patching and sparse autoencoders. The organising idea is a distinction between *observational* methods, which record what activations do, and *causal* methods, which intervene and observe what changes.

Activation patching is the canonical causal method. You run the model on two inputs, take the residual stream activation at layer \(\ell\) from one run, substitute it into the other, and measure the change in the output. The logic is the interventionist's logic: if replacing the activation of component \(x\) changes the behaviour in the way \(x\)'s hypothesised function predicts, that is evidence for the hypothesis in a way no correlational measurement can provide. If the behaviour does not change, the component was not causally responsible for it — regardless of how strongly it correlated.

This is the standard that separates a mechanistic claim from a descriptive one, and it is why Chapter 21 devotes §21.7 to activation patching rather than treating correlation as sufficient. The subtlety is that a negative result is informative only if the intervention is faithful: patching must actually replace the activation without changing the computation elsewhere.

> **Why the logit lens is a lens and not a microscope** (insight)
>
> The logit lens (§21.5) projects an intermediate residual-stream state through the final unembedding matrix, as though decoding stopped at that layer. It is enormously useful and it is *not* the model's actual computation at that layer: the model has a final layer norm, and in a tuned-lens refinement (§21.5.2) a trained translator per layer corrects the mismatch. So the logit lens gives you a hypothesis about what a layer is doing, and the tuned lens gives you a better hypothesis. Neither is a readout the model performs. Treat the lens as a probe, and validate surprising readings with causal methods.

For agentic systems specifically, the payoff of these methods is a sharper kind of diagnosis. When an agent emits a tool call that should not have happened, the interesting question is whether the decision was made in the plan-construction step or in the tool-selection step. Chapter 22, §22.1.1 levels of evidence give the right epistemic posture: behavioural evidence says *that* the agent did it, representational evidence says *what it believed*, mechanistic evidence says *which component was responsible*. Only the third supports a fix, and only the third supports a claim about an architecture.

>

#### An evaluation discipline for your own agents

Both case studies in Part III and Part IV end with evaluation sections, and they agree on method: define the outcome metric, run the same scenario across configurations, and attribute failures to a component rather than to "the agent".

1. Fix a scenario set and hold it constant across configurations.
2. Record full traces: prompts, tool calls, observations, retries, costs, steps.
3. Separate failure classes — planning vs. execution vs. perception vs. formatting.
4. Report cost alongside success: an agent that solves the task in 40 steps may be worse than one that solves it in 6.
5. Re-test after every harness change; the harness is a component with behaviour, not glue.

**Attributing failures in a two-agent pipeline**

- **Symptom** — Wrong final answer in 14% of cases.
- **Hypothesis A** — Planner routed to the wrong specialist tool.
- **Test A** — Score routing accuracy separately from execution accuracy: routing errors account for 9 of the 14 points.
- **Hypothesis B** — Executor mishandled a valid plan in the remaining 5 cases.
- **Fix** — Improve the planner's tool descriptions and add a validation step before execution; re-run the frozen scenario set to confirm the change.

> Separation of concerns is not only good software design — it is what makes an agent measurable.

#### Responsibility, safety and honesty

Agentic systems act. That single property raises the stakes of every design decision: what the agent may change, what it must ask before doing, what it logs, and what it may never do. The book treats safety, security and human oversight as design requirements (§11.5–11.6), and it warns that models are less dependable than conventional software precisely where dependability would matter most.

- Least privilege: give each tool the narrowest scope that works.
- Human confirmation for irreversible actions, with a clear description of what will happen.
- Untrusted content stays data: retrieved text, tool output and web content never carry instructions.
- Log and review: traces are the audit trail, and they are also your test material.
- Do not overclaim: distinguish simulated behaviour from deployed model behaviour, and behavioural evidence from mechanistic evidence.

> **The course-level takeaway** (insight)
>
> An agentic LLM is a designed system: model + harness + tools + memory + evaluation. Every one of those is something you can specify, test and improve. The failure modes are engineering failure modes, and the fixes are mostly engineering fixes — plus the humility to measure before claiming.

> **What Chapter 13 adds to a list of responsibilities** (warning)
>
> Chapter 13 §13.9 adds the part that a checklist usually misses: these responsibilities are **domain-conditional**. "Confirm before irreversible actions" is right in a clinic and merely annoying in a shop, and "an agent asking for clarification or abstaining is preferable to confident error" is a rule about *how much* to ask, which is itself a parameter. A team that writes the safety rules without writing the stakes down will tune them for the domain they happened to build first.

#### The course on one page

The book is organised around three pillars, and the course follows the same structure: **reasoning** (Part II), **acting** (Parts III and IV) and **interacting** (Part V). Chapter 23.3 draws the three together, and the argument it makes is short enough to state here. A model that only produces text is evaluated on the text it produces. Give it the ability to act — call a function, run code, query a database — and it is evaluated on what those actions change, and on the policy it adapts as a result. Give several such agents the ability to interact, and behaviour appears that nobody scripted: cooperation, trust, and norms forming out of repeated exchanges.

*The three pillars, and the limit that shows up in each*

The connection between the pillars is a cycle, and it is the part worth taking away. Reasoning makes better acting and interacting; the data generated by agents that act and interact can then be used to pretrain and finetune better reasoning models. The book presents the cycle as a route past the plateaus in scaling, because an agent that acts generates a training signal that no amount of pretraining data reproduces exactly. The multi-agent laboratory shows the same cycle inside a single session: a critic's feedback is stored and fed back in on the next round, so one round's output becomes the next round's input.

#### Advanced track

##### Advanced: evaluating a system you cannot re-run

Chapter 23 asks what responsible practice looks like when the system under test is a compound of a model, a harness, tools and an environment. The hard part is that agent behaviour is **stochastic in the environment**: the same agent, re-run, may take a different path, so a single run is not a measurement. Chapter 15, §15.2 makes the same point experimentally, and Chapter 14, §14.4 and Chapter 10, §10.3 show what a disciplined evaluation looks like in practice.

The methodological consequences are worth stating precisely, because they change what you record. You need **multiple seeds** or repeated runs, so a single success is not mistaken for a capability. You need a **task distribution**, not a task, because an agent tuned on one task has been evaluated on one task. You need to separate **outcome metrics** (did it solve the task?) from **process metrics** (how many steps, how many tool calls, how much did it cost, did it call the right tool), because two agents with identical success rates can have very different operational profiles — and for a deployed assistant the process metrics are often the ones that matter.

And you need to record the **harness configuration** alongside the result. A result without the prompt template, the tool set, the step budget and the model version is not reproducible. This is the same requirement the chapter 5 case study imposes on students building models from scratch: the deliverable is not just a working system but a system whose behaviour you can explain.

The same care applies to the simulations in this course. Every lab here is deterministic, seeded and reproducible, and that is a deliberate design constraint rather than a convenience: a deterministic simulator can be *asserted on*. You can write a test that says "with capacity 4 and relevance weight 0.8, the agent retrieves the decisive memory item", and that test is a real claim about the teaching instrument. A stochastic demo can only be described. The distinction generalises — a deterministic, logged evaluation harness is exactly what the field needs and what a live demo of a stochastic agent cannot provide.

> **What the textbook leaves open** (source)
>
> Chapter 23, §23.1 is explicit that the technical and societal questions are open, and the concluding parts of the book are deliberately exploratory. Read the advanced chapters (§19–22, marked with an asterisk in the contents) as a map of *research directions*, not as settled results. Several of the claims in them are contested in the wider literature, and the book’s own hedging is part of the content.

##### Advanced practice

**Q. An agent succeeds on one run of a task. Why is this not, on its own, evidence that the agent can do the task? *(advanced)***

- - Because one run is usually a mistake.
- - Because agent behaviour is stochastic in the environment, so a single run is not a measurement; you need repeated runs across seeds and a task distribution.
- - Because success rate is not a valid metric.
- - Because the model changes between runs.

> **Why:** The same agent can take different paths on re-runs, so a single success cannot be distinguished from luck. Evaluation needs repeated runs, a task distribution, and process metrics recorded alongside outcome metrics (Ch. 15, §15.2; Ch. 14, §14.4; Ch. 10, §10.3).

**Q. Why is recording the harness configuration (prompt template, tool set, step budget, model version) alongside a result a requirement rather than good hygiene? *(advanced)***

- - Because it makes the result look more professional.
- - Because a result without it is not reproducible, and the harness is part of the system being evaluated.
- - Because models cannot be versioned.
- - Because the step budget is the only metric that matters.

> **Why:** The unit of analysis for agentic behaviour is the system, and the harness is a large part of it. Without the configuration, a result cannot be reproduced or attributed, so the claim is not a scientific claim (Ch. 22, §22.1.3; Ch. 5, §5.8).

**Attention** — The mechanism that decides, for each token, how much of every other token to mix in. A dot product against every input gives a score; a softmax turns the scores into a probability distribution over the whole input; the context vector is their weighted sum. It is a soft lookup: it never looks at one thing, it looks at everything with a distribution over it.

*Source:* Ch. 2, §2.3.4 Attention

*Related:* Embedding, Context window, Retrieval-augmented generation (RAG)

**Softmax** — The normalisation that turns a list of scores into a probability distribution summing to one. In attention it decides how sharply the lookup is: a flat softmax spreads the weight over everything and the context vector becomes an average, while a sharp one concentrates on a single input.

*Source:* Ch. 2, §2.3.4 Attention

*Related:* Attention, Context window

**Agentic loop** — The repeating reason → act → observe cycle that turns a model into an agent. The harness owns the loop; the model supplies one step of it at a time.

**Tool use** — Calling an external function — a search, a calculator, an API — so that language competence becomes effect. The textbook treats it as the capability that turns an assistant into an agent.

**Generative agents** — Agents given a memory stream, a reflection mechanism and a planning step, so that they accumulate experience and behave consistently over time rather than resetting each session.

**Valence** — Whether an event is good or bad for the agent. The original generative-agents memory system is valence-blind: a criticism and a compliment are encoded and retrieved with equal weight, which is why the case study in Chapter 18 exists.

**Evaluation** — Measuring an agent against a frozen task set with a stated metric, so that a claim about its behaviour can be checked rather than believed.

**Social chain of thought** — Prompting a model to predict the opponent's move before choosing its own. The textbook reports that it improved coordination, and that prediction alone was not enough — the prediction had to be inside the decision loop.

*Source:* Ch. 15, §15.4.1 Coordination in social dilemmas

**Construct validity** — Whether a benchmark measures the thing it claims to measure. The textbook insists on it because a social-dilemma score is evidence about cooperation only if the game really elicits it.

*Source:* Ch. 15, §15.1 What is LLM behaviour?

**Debate** — A multi-agent arrangement in which two or more agents argue a position and a judge decides. The textbook treats it as a way of surfacing disagreement rather than a guarantee of truth.

*Source:* Ch. 16, §16.3.2 Debate and discussion

**Complementary pair** — Two agents with deliberately different roles or prompts, whose errors are less likely to coincide. The textbook frames the pair as more valuable than either agent alone.

**Recall@k** — The fraction of relevant items that appear among the top k results of a retrieval. A retrieval metric that says how much of what matters was actually retrieved, not how the ranking looked.

**Self-Ask** — A retrieval method in which the model decomposes its own question into sub-questions, answers each, and composes the answers. The retrieval is driven by the model rather than by a fixed query.

**Self-RAG** — A model trained to emit a token when it wants to retrieve, so that retrieval becomes a decision the model makes rather than a fixed step in a pipeline.

*Source:* Ch. 12, §12.4.1 Adaptive retrieval via Self-RAG and Self-Ask

**VLM** — A vision-language model: one that accepts images alongside text, so that perception and language are handled by the same model rather than by two separate systems.

*Source:* Ch. 7, §7.1 Multi-modal vision language models

**Workflow node** — One step in a workflow graph — an input, a planner, a tool call, a decision. The node is a course-level abstraction for the control flow the harness executes, not a term from the textbook.

*Related:* Execution trace (course term), Harness, Agentic loop

**Planning** — Producing a sequence of actions towards a goal before executing them. Planning needs a model of the world: a planner that does not know the door is locked will plan straight into it.

*Source:* Ch. 6, §6.1 In-context reasoning

**Backtracking** — Undoing part of a plan and trying a different route. In a search-based planner it is what makes a dead end recoverable rather than fatal.

*Source:* Ch. 6, §6.1 In-context reasoning

**Replanning** — Producing a fresh plan from the current state after something has gone wrong. It is the difference between an agent that retries and one that recovers.

*Source:* Ch. 6, §6.2.4.2 Self-reflection

**Short-term memory** — A bounded working buffer holding the last few steps of a trajectory. It is cheap and immediate, and it is forgotten as soon as the buffer wraps.

*Source:* Ch. 9, §9.3.2 Memory architectures

*Related:* Memory architecture, Episodic memory, Context window

**Episodic memory** — A store of what happened, kept across sessions, so that the agent can recall earlier events rather than only the current trajectory.

*Source:* Ch. 9, §9.3.2 Memory architectures

*Related:* Memory architecture, Short-term memory, Continual learning

**Eviction** — Removing an item from a memory store to make room. The policy that decides which item goes is as important as the one that decides what goes in.

*Source:* Ch. 9, §9.3.2.3 Explicit memory management

*Related:* Memory architecture, Retrieval, Short-term memory

**Retrieval** — Selecting the stored material relevant to the current question. Retrieval is a *ranking* problem, and a bigger store does not by itself make it easier.

*Source:* Ch. 12, §12.1 Retrieval in general

*Related:* Retrieval-augmented generation (RAG), Vector database, Eviction, Recall@k

**Verification** — Checking a result against something that can decide it: a test, a rule, a reference. It is what turns a plausible answer into a checked one.

*Related:* Evaluation, Safety, Human-in-the-loop, Role-based multi-agent system

**Handoff** — The transfer of work from one agent to another. A handoff carries a context, and a lossy handoff silently drops the part the next agent needed.

*Source:* Ch. 16, §16.2 Strategic interaction

**Coordination failure** — A breakdown caused not by any one agent being wrong but by the agents failing to work together: a dropped message, an unverified handoff, a conflict left unresolved.

*Source:* Ch. 17, §17.5 Risks of emergent behaviour

**Model error** — The gap between the model an agent plans inside and the world it actually acts in. It is what makes model-based planning fragile in exactly the situations that matter.

**Sample efficiency** — How much experience an agent needs before it is good. A model-based agent trades per-step computation for fewer interactions, which is the trade the chapter is about.

*Source:* Ch. 7, §7.3.5.1 Model-free reinforcement learning

**Branching** — Routing execution down one of several paths according to a decision. The branch labels are what make the choice legible in the trace afterwards.

*Source:* Ch. 11, §11.2 Tool use architectures

**Error recovery** — What an agent does when a tool fails, an observation is malformed or the context overflows: retry, re-plan, escalate, or report the limitation honestly.

*Source:* Ch. 11, §11.5 Robustness, error handling and recovery

*Related:* Robustness, Self-reflection, Replanning, Tool use

**Decision node** — A node in a workflow graph that routes execution down one of several labelled branches. The engine follows the edge whose label matches the decision.

*Source:* Ch. 11, §11.2 Tool use architectures

*Related:* Branching, Tool use architecture, Harness

**Adaptive retrieval** — Retrieving only when the question needs it. The textbook sets it against the always-on pipeline, which pulls a fixed number of passages whether or not one of them is wanted, and names four ways to get it: gate on the model’s own confidence, retrieve iteratively, plan the query first, or train the model to emit a retrieve token. All four trade a decision for a saving, and the saving is the retrieval that did not happen.

*Source:* Ch. 12, §12.4 Adaptive Retrieval Methods

*Related:* Self-RAG, Self-Ask, Query critique, Retrieval, Retrieval-augmented generation (RAG)

**Query critique** — Grading a retrieval, or the passages it returned, before committing to an answer. Self-RAG does it with reflection tokens the model is trained to emit — retrieve or do not retrieve, relevant or irrelevant — so the judgement is part of generation rather than a second model bolted on afterwards. Lab H implements the same gate as a score against a threshold, so that the threshold can be moved and the cost of setting it wrong counted.

*Source:* Ch. 12, §12.4.1 Adaptive retrieval via Self-RAG and Self-Ask

*Related:* Adaptive retrieval, Self-RAG, Abstention, Verification

**Abstention** — Declining to answer. The textbook puts it in the generation step of the pipeline: when the evidence retrieved is insufficient the model should abstain or ask for clarification. It is the only defence against confident error that is free to honour, which is why an abstention rate is a measurement rather than an apology — and why an abstention is wrong in a different way from a hallucination.

*Source:* Ch. 12, §12.3 Retrieval-Augmented Generation Pipeline

*Related:* Hallucination, Faithfulness, Adaptive retrieval, Query critique

**Question decomposition** — Splitting a question into sub-questions that can each be settled on their own, then composing the answers. Self-Ask does it inside the model’s own prompt, and the reason to do it is that a sub-question is small enough for one retrieval to answer. The cost is the same fact seen from the other side: every hop is now a place where a wrong subject can be picked up and carried forward.

*Source:* Ch. 12, §12.4 Adaptive Retrieval Methods

*Related:* Self-Ask, Multi-hop retrieval, Adaptive retrieval, Chain of thought

**Multi-hop retrieval** — Answering a question no single document settles, by retrieving once per step and using the answer of one hop to form the query for the next. The textbook’s iterative retrieval — pull a few passages, reason about them, decide whether more rounds of search are needed — is the adaptive method built for exactly this. Lab H scores it as hop coverage: of the hops a question requires, how many were covered.

*Source:* Ch. 12, §12.4 Adaptive Retrieval Methods

*Related:* Question decomposition, Adaptive retrieval, Retrieval, Recall@k

**Transfer** — Reusing what was learned in one place as the starting point in another. The textbook’s clearest instance is RT-2, where a web-trained vision-language model is finetuned on robot trajectories so that web knowledge informs control; the LLM training pipeline is the same idea arranged in several phases. What transfer buys is measured in interactions saved on the new task, and the measurement is not guaranteed to come out positive.

*Source:* Ch. 7, §7.2 Decisions & Vision Language Action Models

*Related:* Vision-language-action model (VLA), Finetuning, Negative transfer, Sample efficiency, Distillation

**Negative transfer** — Transfer that costs rather than saves: the inherited starting point is a prior that has to be unlearned before the new task can be learned, so the agent needs more interactions than one that began from nothing. The textbook names the success case and not this one, so the term is used here as the plain name for what Lab E measures — a transferred table replayed against a fresh one on the same seeded task family, with the interaction count of each reported.

*Related:* Transfer, Sample efficiency, Model error, Moving-target problem

**Self-generated data** — Training material produced by the system that will consume it. The textbook has two cases: on-policy distillation, where the student is corrected on sequences it sampled itself, and the scaling argument in §23.2.2, where an agent’s interactions with its environment become pretraining data and vision-language-action models are trained on self-generated action data. The promise is data exactly as hard as the model is; the risk is a loop that feeds on its own output.

*Source:* Ch. 23, §23.2.2 Scale

*Related:* Synthetic data, Compounding model error, Distillation, World model

**Compounding model error** — Error that accumulates because each correction is made against a model rather than against the world. The textbook’s version is the distillation loop: successive generations trained on recursively generated data lose the long tail of the original distribution, and without real-data anchoring the collapse, bias, privacy and licensing risks compound with every iteration. Lab E measures the milder, earlier form — a fitted transition model scored against a fixed probe of the real dynamics, generation after generation.

*Source:* Ch. 19, §19.5.1 Model Collapse

*Related:* Model error, Self-generated data, Synthetic data, World model

**Forgetting curve** — A decay rule for stored memory: the trace of a fact fades with the time since it was last rehearsed, and a rehearsal resets it. The textbook lists forgetting as one of the memory-management operations and points at MemoryBank, whose implementation is this curve; Lab F reproduces the mechanism rather than the paper’s numbers, so the recall interval can be moved and the facts it saves counted against a threshold.

*Source:* Ch. 9, §9.3.2.3 Explicit memory management

*Related:* Hierarchical memory, Consolidation, Episodic memory, Eviction, Memory architecture

**Hierarchical memory** — Stores kept at more than one level of abstraction, where the upper levels summarise the lower. The book’s instance is MemoryBank, which adds hierarchical summaries of a user’s interactions above the event traces and keeps a running profile of the personality those events imply. The gain is that the same facts stay reachable in fewer words for longer; the loss, which Lab F counts fact by fact, is the detail a summary can omit while remaining a good summary.

*Source:* Ch. 9, §9.3.2.3 Explicit memory management

*Related:* Forgetting curve, Consolidation, Memory architecture, Prompt compression, Short-term memory

**Consolidation** — Moving what is worth keeping out of a fast, volatile store and into a slow, durable one. The word appears in the textbook with Mem1, whose compact state is trained by reinforcement learning to incentivise state consolidation — the agent decides what survives the interaction. Lab F treats it as a threshold on the decay curve: a trace that has fallen below a given remembered strength is folded into a summary rather than kept as an event.

*Source:* Ch. 9, §9.3.2.3 Explicit memory management

*Related:* Forgetting curve, Hierarchical memory, Write policy, Episodic memory, Continual learning

**Write policy** — The rule that decides what a memory store adds, updates, deletes or leaves alone. The book frames memory as read and write operations, with compacting and forgetting among the ones that matter; AgeMem then folds the write operations into the agent’s own policy and trains them end to end. Lab F sets the two versions against each other — a hand-written rule and a learned one, both scored on the retrieval that happens later.

*Source:* Ch. 9, §9.3.2.3 Explicit memory management

*Related:* Eviction, Memory architecture, Policy gradient, Consolidation, Retrieval

**Policy gradient** — The family of reinforcement-learning updates that raise the probability of the actions that paid, by differentiating expected return with respect to the policy’s own parameters. The textbook’s memory section says only that write operations are trained with reinforcement learning; this is the name of the rule Lab F applies — a seeded tabular softmax over four write actions. It is defined here because a badge that says *learned* should be answerable when a student asks learned how.

*Related:* Reinforcement learning, Write policy, Consolidation, Sample efficiency

**Decomposable work** — Work that can be split into steps each answerable without holding the final answer already. The textbook’s argument for chain of thought rests on this property: a decoder instructed to answer does answer immediately, whatever it produces, so a problem has to be worked into a sequence of steps before the model can be made to walk them. It follows that longer chains pay where the steps exist and cost where they do not — which is what Lab G sweeps rather than asserts.

*Source:* Ch. 6, §6.1.3 Chain of thought prompting

*Related:* Chain of thought, Reasoning, Overthinking, Question decomposition, Verification

**Overthinking** — Reasoning that becomes worse as it becomes longer. The textbook lists it among the limits of scaling: chain of thought works better in some domains than others, and deeper reasoning may lead to overthinking, where the process becomes less effective as more effort is spent. Lab G’s crossover is the same phenomenon measured on a battery — the depth at which a longer chain stops beating a shorter one, and the tokens it spent to find that out.

*Source:* Ch. 23, §23.2.2 Scale

*Related:* Chain of thought, Decomposable work, External verification, Reasoning

**External verification** — A check the model cannot perform by continuing to generate: a test, a calculator, a deterministic function, a second source. The textbook’s sharpest instance is reinforcement learning with verifiable rewards, where a deterministic function decides whether a sampled completion is correct and the reward follows. It matters because reflection alone does not supply it — an interaction style whose own steps are never answered by the world has nothing to correct against.

*Source:* Ch. 6, §6.2.4.3 RL with Verifiable Rewards

*Related:* Verification, RLVR, Reflexion, Self-reflection, Overthinking

**Provenance** — Where a claim came from, recorded so that it can be checked. The textbook’s measurable version is KILT, which scores knowledge-intensive tasks alongside the citations a model produced, encouraging models to cite the passages they used. Lab G applies the same rule to its own screens: a figure is printed either as measured here or as reported elsewhere with its citation, and a cell that mixes the two — a reported claim carrying a digit — is refused rather than displayed.

*Source:* Ch. 12, §12.7 Evaluation

*Related:* Recall@k, Mean reciprocal rank (MRR), Faithfulness, Levels of evidence, Evaluation
